# «Знаю» и избранное — установленная причина отказа

18 октября 2026. **Причина подтверждена реальным ответом Supabase, предоставленным пользователем. Серверная правка подготовлена, но не применена: выполнять SQL в этом задании запрещено. Облачное сохранение на проблемном слове до исправления сервера остаётся заблокированным.**

## Диагноз

Ответ `POST /rest/v1/rpc/sl_apply_event`: HTTP 400, SQLSTATE **23514**, сообщение:

```text
new row for relation "sl_words" violates check constraint "sl_words_interval_days_check"
```

Сервер пытался записать **390744** дня. В `202610170001_core.sql` допустим `interval_days between 0 and 365000`. Функция `sl_private.review` из 003 при правильной оценке умножает предыдущий интервал на ease и округляет, но не ограничивает результат этим максимумом. Например, **130248 × 3 = 390744**. Это накопительный дефект планировщика, проявляющийся на словах с длинной историей повторений; не доказательство потери click listener после последних JS-правок.

`mark_known` вызывает этот helper внутри `sl_apply_event`. Нарушение CHECK откатывает весь запрос: нет подтверждённой отметки, события или выплаты XP. Неудачный запрос остаётся pending в начале durable-очереди. `favorite_set` сам не меняет SRS, но следующие запросы ожидают неуспешный первый. Поэтому пользователю кажутся сломанными обе кнопки. Ошибка 23514 раньше превращалась в общее сообщение и повторялась таймером каждые 15 секунд.

Идентификатор пользователя и полный failing row из ответа не сохранялись в файлы отчёта.

## Подготовленное исправление

[Полный серверный патч](../supabase/patches/srs_interval_cap.sql) заменяет только `sl_private.review`: результат расчёта ограничивается существующим максимумом `least(365000, ...)`. Остальные части функции совпадают с 003. Нет нового алгоритма XP, публичного RPC, изменения таблиц, очистки данных или перерасчёта существующих записей. SQL лежит в `supabase/patches`, не включён в автоматические миграции/сборку и не зависит от неустановленной XP-миграции 012.

Функция остаётся SECURITY INVOKER с пустым search_path. Клиентские права EXECUTE явно отозваны. Пользовательская привязка по-прежнему выполняется существующим public RPC. Существующие XP, known_rewarded, история и SRS не обнуляются. При последующем успешном событии сервер штатно обновляет SRS, сохраняя допустимый интервал.

**Патч не выполнялся ни локально через SQL, ни в Supabase.** Его совместимость с 001–011 проверена статическим сравнением исходников; выполнение PL/pgSQL и настоящий Supabase acceptance ещё нужны после отдельного разрешения. Нельзя объявлять рабочую базу исправленной по результату JS-модели.

Клиентские исправления:

- Ошибка распознаётся по 23514 и точному имени CHECK, показывается понятный текст об ошибке расписания и ожидающих изменениях. Raw details с персональными данными не сохраняются/не выводятся.
- Прекращается бесполезное повторение этой ошибки 15-секундным таймером. Ручной retry остаётся, UUID и тела событий сохраняются, очередь не удаляется и не обходится.
- «Знаю» сразу получает pending-индикацию; повторные быстрые клики коалесцируются. Отметки обновляются только из серверного snapshot после ACK.
- Делегированный click явно обрабатывает rejected Promise и показывает ошибку, не сообщает об успехе.
- Обновлены query-версии app/progress и RELEASE SW. На loopback worker и до правки загружал runtime из сети; Supabase-запросы не кешируются. Кеш не является причиной подтверждённого серверного CHECK failure.
- Дизайн, награды XP, readiness/capability checks, owner checks, обработка revision conflicts и guest/account isolation сохранены.

## Что проверено автоматически

`tests/word-buttons-integration.cjs` загружает production app.js, supabase-rpc.js и supabase-progress.js в DOM/VM. Действия отправляются настоящими DOM click/input/change через штатные bindEvents, очередь и RPC adapter. Backend, Auth и IndexedDB смоделированы, это не реальный Supabase.

- «Знаю» → mark_known → ACK → изучено; ещё клик → unmark_known → снято; повторное изучение не даёт второй награды.
- Избранное → favorite_set(true/false), только серверное подтверждение меняет состояние.
- Поиск и фильтр через input/change, динамическая замена карточек, flash next, word detail, вложенный span кнопки, двойной клик и pending.
- Поиск и карточки сохраняют DOM identity после ACK; полного render при изменении слова не происходит, фильтры не сбрасываются. Геометрия/визуальные скачки в настоящем браузере не измерялись.
- Reload и переключение A/B/A восстанавливают правильный account snapshot. Гостевые bytes остаются неизменными; гостевые клики не отправляют RPC.
- Отказ сервера не меняет selected state; rejected action не создаёт unhandled rejection.
- Воспроизведён CHECK failure из ответа пользователя: очередь ждёт, обе кнопки не показывают ложного успеха, XP/SRS серверной модели не изменяются. Затем **модель** серверного helper переключается на ограниченный интервал: ручной retry отправляет прежние UUID/body, подтверждает оба действия, не дублирует XP; повторное обучение на границе и reload работают.

`tests/srs-interval-contract.cjs` статически сверяет предел с таблицей 001, сравнивает весь helper с 003 (отличие — только least), проверяет приватность и отсутствие включения патча в авто-миграции. SQL не исполняется.

Полный JS/CJS набор, синтаксис, manifest и diff проверяются отдельно. Устаревшая проверка legal translations в quality.cjs искала буквальную строку `ru:`; после предыдущего обновления юридические словари используют JSON-ключ `"ru"`. Проверка исправлена на разбор реального I18N и наличие всех четырёх языков, без правки юридических страниц в этом задании.

## Ручная проверка и условие завершения

1. Перезагрузить текущий сайт без очистки хранилищ. Пока сервер не исправлен, на проблемном слове ожидается сообщение об ошибке расписания; это честный отказ, а не восстановленное сохранение.
2. Отдельно согласовать проверку и установку **только** `supabase/patches/srs_interval_cap.sql`. Не применять ради этой проблемы XP 012, не запускать тестовые fixtures и не сбрасывать слово неправильным ответом. В этом задании установка не выполняется.
3. После серверного исправления нажать существующую кнопку «Повторить отправку». В Network первый pending `sl_apply_event` должен получить HTTP 200, затем — следующие события. Не очищать IndexedDB и не создавать заменяющие UUID.
4. На `arbeta` и другом слове: «Знаю» → включено → ещё раз → выключено → ещё раз → включено. За повторное изучение нет новых XP, при снятии XP не списываются. Проверить ⭐ в обе стороны.
5. Сравнить Request Payload по типам mark_known/unmark_known/favorite_set и Response `progress.state.known/favorites`; не публиковать Authorization, токены и полный failing row. Успех должен подтверждаться ответом сервера, а не только цветом кнопки.
6. Повторить после поиска, фильтров, перехода в слово и переключения flashcards. Обновить страницу, выйти/войти: выбранные состояния сохраняются. На втором устройстве проверить тот же аккаунт; на другом аккаунте — отсутствие чужих отметок.
7. Проверить гостевой режим отдельно: переключения работают локально, гостевые данные не попадают в аккаунт. Проверить Network/Console на неожиданные ошибки, mobile tap и отсутствие визуальных скачков.
