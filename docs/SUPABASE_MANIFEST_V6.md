`sl_private.manifest()` через `CREATE OR REPLACE FUNCTION` внутри транзакции.
Сигнатура `() returns jsonb`, язык SQL, IMMUTABLE, SECURITY INVOKER и
`SET search_path = ''` сохранены. CREATE OR REPLACE сохраняет владельца,
OID и существующие ACL. GRANT/REVOKE, операции с таблицами и SQL-вызовы импорта

## Изменённые проверки

`scripts/check_supabase_manifest.py` находит последнюю миграцию, определяющую
именно `sl_private.manifest()`, и сравнивает её полный JSON с актуальным
`current_manifest()`. Отдельная защита этой версии требует равенства всех
ID, категорий и количеств вопросов исходной миграции 002.
Будущие изменения каталога потребуют отдельного пересмотра этой защиты.

`scripts/test_supabase_local.py` применяет первые пять миграций в новом
одноразовом кластере. Перед шестой запускает
`supabase/tests/002_manifest_upgrade.sql`, который сам применяет шестую миграцию
поверх искусственных данных. Он фиксирует содержимое всех семи таблиц и
параметры pg_proc перед обновлением, проверяет их сохранность после, затем
в отдельной откатываемой транзакции проверяет старую/новую версию клиента и
завершение старой активной сессии. Тестовые фикстуры нельзя запускать на реальной БД.
Скрипт не принимает URL базы, не слушает TCP, не использует Supabase CLI и
останавливает временный кластер после теста.

## Совместимость и порядок будущего применения

До отдельного разрешения SQL в реальном Supabase не выполнять. Учебную облачную
запись не включать: несовместимость старых клиентов для новых сессий подтверждена.

После замены манифеста `sl_get_progress()` будет возвращать новую версию всем
клиентам, без сброса revision у существующего аккаунта. Он по-прежнему может
создать пустую строку аккаунта, если её не было: это прежнее поведение RPC,
а не действие шестой миграции.

`session_start` со старой content_version получает unsupported_content_version.
Тест подтвердил, что отказ не меняет revision и не мешает последующему запросу
с новой версией. Новая версия начинает сессию успешно.

Для уже начатой старой сессии `answer` и `session_finish` используют сохранённые
questions и не требуют совпадения исторической версии с текущим манифестом.
Тест завершил такую сессию и подтвердил сохранение старой content_version.
Конфликты expectedRevision между устройствами продолжают требовать обычной
обработки; миграция их не отменяет. Локальные незавершённые квизы остаются в
sessionStorage и не становятся облачными сессиями.

При будущем согласованном применении:

1. Проверить, что выбраны нужные Supabase-проект и схема, применены 001–005,
   а удалённый старый манифест соответствует локальному 002 по полному JSON.
   Сохранить актуальную резервную копию базы и параметры/ACL функции.
2. Повторить локальный расчёт и сверку контента перед применением; не менять
   учебные файлы между расчётом и выпуском.
3. Применить только подготовленную 006 в согласованное окно. Обеспечить обновление
   старых клиентов до подключения учебной записи. Поддержка двух версий требует
   отдельного изменения RPC и в этой миграции не реализована.
4. Сверить полный удалённый манифест и новую версию. Проверить сохранность
   revision, данных и исторических сессий у существующих аккаунтов, owner и ACL.
   Не запускать тестовые SQL-фикстуры против production.
5. На актуальной локальной странице получить свежий облачный снимок новым сеансом
   или перезагрузкой. Готовый снимок SVProgress кешируется в памяти, поэтому
   повторный preview сам по себе его не обновит.
6. Повторить предпросмотр, сохраняя разделение гостя и аккаунта. Проверить,
   что нет вызовов sl_import_progress/sl_apply_event. Решение об импорте и
   включении синхронизации принять отдельно.

Подготовка не включает изменение предыдущих миграций, реальных данных,
localStorage, резервных копий или IndexedDB. Импорт, деплой и выполнение SQL
в реальном Supabase не выполнялись. Ранее внесённые изменения frontend и
предпросмотра сохранены без дополнительных правок в рамках этой задачи.
