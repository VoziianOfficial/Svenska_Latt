## 1. Подготовить и проверить пакет без публикации

Из корня репозитория:

```sh
python3 scripts/build_pronouns_release.py
python3 scripts/check_supabase_manifest.py
python3 tests/pronouns-release.py
node tests/pronouns.cjs
node tests/supabase-preparation.cjs
```

Генератор только записывает предложение 021, read-only проверки и клиентский manifest. Он не подключается к БД и не исполняет SQL. Генераторы старых 018/019/020 для выпуска не запускать; ни один из этих SQL-файлов не редактировать и не применять повторно.

Реальные SQL-проверки доступны отдельной командой:

```sh
python3 scripts/test_pronouns_sql.py
```

Она сама создаёт новый каталог `/private/tmp/sl-pronouns-sql-*`, PostgreSQL-кластер и приватный Unix-сокет; TCP отключён, переменные PG удалены из окружения дочерних процессов, адрес внешней БД передать нельзя. Пустая схема создаётся из 001–017. **Файлы миграций 018, 019 и 020 не исполняются**: тестовая копия состояния 020 создаётся из сохранённых определений функций и сверяется со всеми четырьмя предоставленными MD5. Затем исполняется только кандидат 021. Кластер останавливается и при ошибке, журналы сохраняются.

Для браузерных проверок используется отдельный временный профиль Chrome и локальный HTTP-сервер:

`SL_BROWSER_PORT` по умолчанию 9224. Queue-тест использует настоящие IndexedDB и Web Locks, а Auth/RPC внутри iframe — тестовые. Он не создаёт пользователей в Supabase и не удаляет очередь. Проверки не следует направлять на обычный пользовательский профиль браузера.

Сборка в новую папку, без размещения на хостинге:

Папка должна отсутствовать: генератор не перезаписывает существующую сборку. Он включает новый урок, `supabase-progress.js`, версии ресурсов из `index.html` и выводит `release-manifest.json`. ## 3. Применить только 021 одной транзакцией

Этот этап изменяет рабочую БД и сейчас агентом не выполняется. После отдельного решения оператора о применении открыть **полный** `202611220021_pronouns.sql` в Supabase SQL Editor и выполнить целиком от `BEGIN` до `COMMIT`. Не исполнять отдельные внутренние блоки по выборке.

Альтернативно, в локальном терминале оператора, если `DATABASE_URL` уже настроен именно на нужную БД:

```sh
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f supabase/migrations/202611220021_pronouns.sql
```

Эти команды приведены для ручного выполнения; агент их к production не запускал. Проверка preflight сама ничего не изменяет. Внутренние guards 021 повторяют проверку прямо в транзакции, поэтому устаревший preflight не разрешит незаметно применить SQL поверх другого состояния.

Если в транзакции возникла ошибка, файл не должен дойти до COMMIT. При оставшемся в SQL Editor открытом aborted transaction выполнить `ROLLBACK;`, затем повторить read-only preflight: четыре MD5 и версия должны остаться исходными. Проверки с принудительной ошибкой **после замены catalog, reader, writer и manifest** подтвердили полный откат и неизменность пользовательских строк.

Срабатывание `historical lesson reward reservation missing` означает остановку для разбора истории. Оно не является разрешением пометить старые награды или дописать XP задним числом.

## 4. Проверить сервер до публикации клиента

Выполнить read-only postflight целиком. Должны быть:

- `content_version = static-57b40b608d91091d` и `version_ok = true`;
- все четыре `function_ok = true`, MD5 равны столбцу «после 021»;
- `active_24`, `total_35`, `reward_35`, `other_banks_unchanged`, `archive_unchanged`, `frozen_020_version_ok`, `answer_bank_private` — все `true`.

```sh
psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f supabase/checks/021_pronouns_postflight.sql
```

После структурного postflight повторить тот же read-only аудит до публикации и любых тестовых прохождений:

```sh
PGOPTIONS='-c default_transaction_read_only=on' psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f supabase/checks/021_pronouns_postflight.sql > /private/tmp/pronouns-021-postflight.txt
PGOPTIONS='-c default_transaction_read_only=on' psql "$DATABASE_URL" -X -v ON_ERROR_STOP=1 -f supabase/checks/021_pronouns_data_audit.sql > /private/tmp/pronouns-021-data-after.txt
diff -u /private/tmp/pronouns-021-data-before.txt /private/tmp/pronouns-021-data-after.txt
```

В спокойном окне обновления `diff` должен быть пустым: 021 не меняет XP, результаты и историю. Если параллельно проходило обучение или синхронизация, агрегаты могут законно измениться; такой `diff` сам по себе не доказывает повреждение. Разобрать причину до публикации, не выравнивать данные SQL-правками. Аудит не вызывает `sl_get_progress` или `sl_apply_event`, не запускает тест и не начисляет XP. Проверки 19/20/24, повторов и отката уже выполнены на локальных фикстурах; реальное прохождение тестового аккаунта после выпуска — отдельное действие с записью прогресса.

До успешной проверки клиента не публиковать. С момента COMMIT 021 до загрузки нового клиента старый клиент 020 временно закрывает запись из-за несовпадения текущего манифеста. Это ожидаемая защита: полностью непрерывной записи для уже открытых старых вкладок этот порядок не обещает; запросы остаются в очереди. Новый клиент с ещё не обновлённым сервером тоже закрывает запись, поэтому публиковать его первым нельзя. Не устранять это очисткой хранилищ. После загрузки согласованного клиента очередь из 020 может передавать исходные события без их преобразования.

Отдельно разместить весь runtime из проверенной сборки. Не смешивать старые `app.js`/`supabase-progress.js` с новым `lessons.json`. После обновления страницы войти в обычный тестовый аккаунт и проверить состояние:

Проверить открытие главы, 24 вопроса нового теста и отдельный результат; старые результаты первых двух уроков и награды должны остаться прежними. Для аккаунта, уже получившего награду lesson-3, повторное прохождение новой версии не даёт ещё 35 XP. Такие действия с реальным тестовым аккаунтом после выпуска — отдельные ручные приёмочные действия; они не выполнялись агентом. Функциональные проверки до выпуска проводились на локальных фикстурах.

Старые подтверждённые сессии продолжаются по сохранённым ID. Старые неподтверждённые старты 020 используют замороженный банк 020. Новый набор из 24 ID нельзя отправить под версией 020, а набор из 11 старых ID — под версией 021: сервер отклоняет смешение поколений. Неизвестные версии, конфликтные и ранее отклонённые события требуют разбора; записи сохраняются и автоматически не переписываются.

## Ошибка после COMMIT

`ROLLBACK` не отменяет уже выполненный COMMIT. Если postflight не прошёл, остановить публикацию и сохранить фактический read-only отчёт. Не запускать 018/019/020 для «возврата» и не откатывать только manifest отдельно от банков/функций. Исправление готовится следующей самостоятельной миграцией от измеренного состояния. До него сохраняются БД, события и квитанции; принудительная очистка очереди не используется.
