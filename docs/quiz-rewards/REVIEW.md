# Svenska Lätt: тесты и однократные XP — проверка перед релизом

Дата: 18 октября 2026. Изменения подготовлены и проверены локально. Реальный Supabase, его Auth/PostgREST и браузер с настоящим аккаунтом **не тестировались**. Деплой и SQL на удалённой базе не выполнялись. Это не подтверждение готовности к production.

## 1. Прежние начисления

Источники: `app.js`, серверный `sl_apply_event` из миграций 003 и 007. Последующие 008/009 не меняют эту логику.

| Действие | До изменения | После изменения |
|---|---:|---:|
| Правильный ответ теста | 12 XP | 0 XP |
| Неправильный ответ теста | 3 XP | 0 XP |
| Первое завершение урока | 35 XP при ≥60% | 35 XP при ≥80%, однократно |
| Ответы повторной попытки | Снова 12/3 XP за каждый ответ | 0 XP |
| Ответы незаконченной попытки | XP сохранялись | 0 XP |

Например, урок из 10 вопросов на 8/10 давал 137 XP: 8×12 + 2×3 + 35. Следующее прохождение на 10/10 добавляло ещё 120 XP. Тесты книг, тем, видео и случайные тренировки тоже использовали оплачиваемый `answer`.

Отдельные действия сохранены: первое изучение слова — 8 XP с защитой 007; `review_grade` — 0; отрицательный `flash_grade` — 2; отметка книги прочитанной — 20; отметка видео просмотренным — 5. У `video_set` и отрицательного `flash_grade` остаются прежние возможности повторного начисления. Эти действия не являются тестами; их экономику эта миграция намеренно не меняет. «Прочитано» и «Просмотрено» не считаются доказательством сдачи соответствующего квиза.

## 2. Принятая модель наград

| Тип | Текущий объём | Награда за ≥80% | Стабильный ID |
|---|---:|---:|---|
| Урок (50 тестов) | 9–13 вопросов | 35 XP один раз | `lesson:<lesson-id>` |
| Книга (12 тестов) | 7 вопросов | 35 XP один раз | `book:<book-id>` |
| Тема (42 теста) | 20 разных слов из пула темы | 35 XP один раз за тему | `topic:<category>` |
| Видеоквиз (9 тестов) | 1 вопрос | 12 XP один раз | `video:<video-id>` |
| 14 случайных режимов, чтение в случайном режиме, SRS-тренировка | Новый набор при повторе | 0 XP | `practice:<mode>` для лучшего результата режима |

35 XP — уже существующая награда за освоение урока. Она сохранена как единая награда за завершение учебного теста книги/темы, без прежней оплаты каждого ответа. 12 XP для короткого видеоквиза соответствует прежней цене единственного правильного ответа; 35 XP за один вопрос было бы непропорционально существующему уроку. Случайные режимы остаются доступными без лимита, обновляют статистику/SRS и сохраняют лучший результат режима, но не создают бесконечную валюту. Лучшие проценты случайных наборов описывают режим, а не отдельное постоянное задание.

Равный бонус 35 XP — намеренно простая модель достижений, а не оплата времени или количества ответов. Это предложение на основе существующих наград, а не вывод из продуктовой аналитики: данных об удержании/скорости обучения в репозитории нет.

Порог проверяется целыми числами: `correct * 5 >= total * 4`. Лучшие результаты сравниваются дробями через перекрёстное умножение. Процент на экране округляется вниз: результат ниже 80% не выглядит как 80%. Награда не зависит от языка, порядка вопросов, UUID попытки или версии контента.

## 3. Сервер и восстановление

Полный самодостаточный SQL, включая доверенный каталог ответов: [`202610180010_quiz_rewards.sql`](../../supabase/migrations/202610180010_quiz_rewards.sql). Существующие миграции 001–009 не изменены.

- `sl_quiz_results`: уникальная пара `(user_id, quiz_id)`, лучший результат, признак уже выданной/исторически зарезервированной награды и ссылка на награждённую попытку.
- Завершение сессии, обновление результата, начисление XP и квитанция события происходят в одной транзакции `sl_apply_event` под общей блокировкой аккаунта. RLS разрешает чтение только владельцу; клиентских INSERT/UPDATE/DELETE нет.
- Полнота проверяется по числу заданий, счётчику ответов и количеству событий `answer`. На каждый индекс есть уникальный ответ. Неполная/брошенная попытка не оплачивается.
- UUID события и точное тело сохраняются в IndexedDB до отправки. Повторный UUID возвращает исходную квитанцию; другое тело с тем же UUID отклоняется. Повтор finish с новым UUID на завершённую попытку отклоняется.
- Два устройства сериализуются блокировкой и проверкой revision. После конфликта очередь повторяет исходный UUID/тело с актуальной revision. Вторая успешная попытка уже видит `rewarded=true`.
- `quiz_result` хранится в событии на сервере и в локальной квитанции. Потеря ответа после commit не теряет награду и не создаёт вторую.
- Интерфейс ждёт серверного подтверждения ответа/finish, а не одной постановки в очередь. При потере связи остаётся повторяемый intent. После подтверждения показывает правильность и объяснение, в конце — счёт, процент, новый рекорд, фактическую награду либо «Тест уже пройден».
- Сессия вкладки сохраняет порядок заданий, ввод, выбранный вариант, язык и неизменяемые события; перезагрузка той же вкладки продолжает попытку. Итоги и XP аккаунта возвращаются сервером после входа. Закрытие вкладки может оставить активную попытку на сервере: она не оплачивается, новый старт разрешён. Перенос незавершённой вкладки на другое устройство не реализован.
- Новый клиент начинает тесты только при capability `quiz_rewards_v1`, поэтому до миграции не отправляет новые события старому оплачивающему серверу. Отдельные действия продолжают работать по прежнему контракту.

### Проверка ответов и предел защиты

Для 113 учебных квизов клиент отправляет `question_id` и выбранный канонический `response`, а не `correct`. Сервер проверяет количество вопросов, уникальность ID, принадлежность банку конкретного теста и сравнивает ответ со своим закрытым каталогом. Для темы допустимы 20 разных слов её действительного пула, `word_id` для SRS берётся с сервера. Каталог генерируется `scripts/quiz_catalog.cjs` из актуального контента; JS-тест проверяет совпадение с встроенным SQL и все 113 тестов на четырёх языках.

Случайные режимы и сессии, начатые до миграции, по-прежнему принимают клиентский `correct`; **они не могут получить новую тестовую награду**. Их статистика не является доверенной оценкой. Исторические результаты также нельзя задним числом сделать доверенными.

Это защита от повторных начислений и подмены флага правильности, а не доказательство самостоятельного решения. Учебные ответы доступны в статическом приложении; автоматизированный клиент может прочитать их и один раз решить конечные тесты. Система не доказывает просмотр видео. Перенос проверки на сервер не следует рекламировать как полную защиту от читов. При следующем изменении контента нужен согласованный серверный каталог с сохранением банка активных версий; ID награды должен остаться прежним.

## 4. Переход старого прогресса

Аккаунтные XP, исходные события, результаты, завершённые уроки, слова, избранное, очередь повторений и учебное время не удаляются и не обнуляются.

Backfill восстанавливает лучший результат по завершённым сессиям. Для импортированного урока без точных счётчиков используется сохранённый `best_percent`, представленный дробью с точностью до 0,000001 процентного пункта вниз; исходное значение в `sl_lessons` не меняется. Это не выдуманное число правильных ответов. Точные дроби новых сессий сохраняются непосредственно.

Консервативный переход резервирует награду, если:

1. В истории этого теста уже есть любые XP (в том числе старые оплаченные ответы незаконченной/неудачной попытки).
2. Есть историческая завершённая попытка ≥80%, даже если событие бонуса отсутствует.
3. Сохранён исторический `completed` урока, в том числе после импорта и при старом пороге 60%.

Таким образом старые оплаченные 6/10 не получают новую награду после 9/10. Сценарий **новых** правил «6/10, затем 9/10» получает 35 XP во второй попытке. Это намеренная консервативная трактовка «за тест уже выдавались XP»; она исключает повторную оплату и не списывает заработанное.

Историческое `completed=true` при 65% сохраняется как достижение, но новая карточка показывает «Лучший результат: 65%», без зелёного статуса ≥80%. Отсутствие исторического процента не заменяется на 100%. В гостевом режиме достоверно известны лишь локальные результаты новой модели и прежний флаг завершения урока: подробной прежней истории книг/тем у гостя нет. История аккаунта берётся из Supabase, гостевые XP автоматически не импортируются.

Незавершённые старые сессии продолжают принимать старый формат ответов без XP. Для нового доверенного квиза можно начать новую попытку. В исходном репозитории был отдельный ещё не установленный `010_study_time_default.sql`. По условию пользователя установлены только 001–009, поэтому тот файл перенумерован в **011** без изменения SQL; теперь версии миграций уникальны. Если в конкретной среде 010 всё-таки уже установлена, сначала нужно согласовать её реальную историю, а не запускать этот план автоматически.

## 7. Безопасная установка и ручная проверка

1. Сначала просмотреть полный SQL 010. Сделать резервную копию реальной БД и получить перечень установленных версий; ожидаются 001–009. Сохранить контрольные суммы/выгрузки XP, событий, уроков, слов, очереди и учебного времени. Резервная копия должна восстанавливаться в отдельную среду.
2. В отдельном staging Supabase, воспроизводящем 001–009 и старые данные, применить **только 010**, проверить backfill, RLS и RPC с настоящими JWT двух пользователей. Таблицы/функции из `supabase/tests` в Supabase не устанавливать. Проверить также сочетание с независимой 011 при её планируемом включении.
3. Старые открытые вкладки после 010 не смогут начать новый fixed-тест без `question_id`; ранее начатые старые сессии сохранят совместимость без XP. Подготовить согласованное обновление клиента и информирование об обновлении, не удаляя очередь и локальный прогресс. В production сервер обновляется первым; новый клиент до 010 закрывает старт тестов через capability. Не откатывать сервер на оплачиваемые `answer` после включения нового клиента.
4. В staging открыть аккаунт A в двух браузерах/устройствах. Для ещё не награждавшегося урока из 10 вопросов: 7/10 → статус 70%, XP неизменны; 8/10 → пройден и +35; 10/10 → рекорд 100%, «Тест уже пройден», XP неизменны. Для другого теста: 6/10 → 9/10, награда только во второй попытке.
5. Проверить 8/11 и 9/11, книгу (+35), тему (+35), видеоквиз (+12); повтор каждого — 0. Любые случайные режимы и повторения — без тестовых XP. Объяснения остаются после каждого вопроса, кнопки старта и повтора всегда доступны.
6. На середине теста обновить вкладку; проверить задания/порядок/ввод/ответ. Включить Offline до отправки ответа и до finish, затем восстановить связь. Отдельно оборвать ответ сервера после commit; повторить исходный intent. Итоговая сумма и одна серверная награда должны совпасть, сообщения об успехе до ACK нет.
7. Дважды нажать finish, повторить тот же HTTP event UUID и завершить две разные попытки одного теста одновременно на устройствах. Допустим конфликт revision и безопасный retry; суммарная награда одна. С другим JWT попытаться прочитать/изменить чужой результат: доступа нет.
8. Выйти и войти заново; проверить XP/лучшие результаты, затем другой аккаунт (изоляция). У аккаунта со старым 65% старое достижение сохранено, новый статус ниже 80%; после 100% новый лучший результат без повторной выплаты. Сравнить слова, избранное, SRS, ручную очередь и учебное время с контрольными данными.
9. Только после этих реальных Supabase/браузерных проверок отдельно согласовывать production-установку и публикацию. В рамках этой задачи они не выполнялись.
