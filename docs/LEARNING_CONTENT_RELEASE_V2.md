# Выпуск пилота и совместимость Supabase

## Почему нужен новый манифест

`scripts/check_supabase_manifest.py` вычисляет версию по **всем исходным байтам** `words.json`, `lessons.json`, `books.json` и каталогу ID. Замена теории и добавление формирующей практики в `lessons.json` меняют эту версию, хотя 511 зачётных вопросов, их порядок, ключи, ID уроков и остальные сущности не меняются. `supabase-progress.js` сверяет версию перед записью; выпуск только клиентских файлов приведёт к `CONTENT_VERSION_MISMATCH` для аккаунтов.

Необходимо отдельное обновление возвращаемого значения `sl_private.manifest()`. Подготовленная новая миграция `supabase/migrations/202611090017_learning_content_manifest.sql` заменяет только эту функцию, сохраняя сигнатуру, SECURITY INVOKER, IMMUTABLE, search_path, владельца и ACL. Каталог полностью прежний, меняется только `version`. Миграция не создаёт/не меняет таблицы, не выполняет DML, не меняет банк ответов, награды, исторические результаты или схему прогресса. Старые миграции не редактируются.

SQL подготовлен как отдельный рецензируемый артефакт; **в этой сессии ни к локальной пользовательской, ни к удалённой базе он не применялся**. Изменений схемы хранения не требуется. Обновление полной платформы и замена зачётного банка остаются последующими этапами.

## Порядок будущего выпуска

1. Провести независимую языковую редактуру пилота и визуальную проверку в настоящем браузере, включая мобильный экран, клавиатуру, смену языка и письмо. Прочитать журнал источников и открытые вопросы программы 2027.
2. Проверить SQL в одноразовом staging на копии текущей конфигурации: различаться должна только версия; сравнить таблицы, награды, права функции и возможность завершения исторической сессии. Проверить очередь офлайн-событий старой версии: её нельзя удалять ради обновления. При несовпадении версия должна явно блокировать запись до безопасного обновления/согласования; не выдавать повторный XP.
3. После отдельного решения о выпуске согласованно обновить манифест и статические файлы. Не публиковать новый клиент со старым серверным манифестом. Данные/очередь не очищать.
4. Для PWA использовать существующий `scripts/build_deploy.py`: он вычисляет release по всему содержимому и меняет RELEASE в копии `sw.js`. Сам Service Worker и его кэширование в этом этапе не редактируются. Auth и локальное/облачное сохранение не меняются.
5. После выпуска проверить гостя и аккаунт, отсутствие дополнительной награды за новые формирующие упражнения, прежний зачётный тест и историю результатов. Новые ответы не считаются освоением старого зачёта, а старые результаты не подтверждают освоение пилотной практики.

Конкретные команды и результаты текущих проверок — в `LEARNING_CONTENT_V2_RESULTS.md`. Подготовка SQL и совпадение каталога не означают, что его применение к production или поведение реального Supabase уже проверены.
