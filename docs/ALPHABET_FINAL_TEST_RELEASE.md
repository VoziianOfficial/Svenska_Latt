## Новый контракт

- Банк `alphabet-final-v1`, 20 активных ID `alphabet-final-v1-q01` … `alphabet-final-v1-q20`; 80% = 16/20.
- Прежние 13 ID `q0` … `q12` и их правильные ответы сохранены в архивном `lesson-1.questions` и в доверенном серверном каталоге. Они доступны для завершения существующих серверных сессий, но не входят в набор новых стартов.
- Контекст сессии остаётся `mode=lesson`, `context_id=lesson-1`, `quiz_id=lesson:lesson-1`. Это сохраняет существующий единый ключ награды 35 XP. Создание нового reward ID дало бы повторную награду и намеренно не используется.
- Исторический агрегат `quizResults['lesson:lesson-1']` сохраняет прежний лучший результат. Новый показатель `quizResults['assessment:alphabet-final-v1']` отдельно отражает освоение нового теста; он не получает самостоятельную награду.
- В интерфейсе прежний результат вынесен в «Историю результатов урока». Только результат нового банка зажигает зелёный статус итогового теста. Прежняя награда отображается как уже полученная, без объявления новой темы пройденной.

## Предложение 019

`scripts/build_alphabet_final_release.py` воспроизводимо создаёт `supabase/migrations/202611160019_alphabet_final_test.sql` и синхронизирует версию клиента с текущими JSON и каталогом. Он не подключается к БД. Версию следует проверять через `python3 scripts/check_supabase_manifest.py`; на момент этой проверки — `static-5e8f29c4d0bd02fe`.

Миграция выполняет банк, read-model и manifest в одной транзакции:

1. Проверяет точные MD5 `prosrc` установленных catalog/reader/writer из просмотренного контракта 014. Неизвестные серверные изменения приводят к отказу, а не к перезаписи.
2. Read-only preflight проверяет исторические завершённые уроки/положительные XP-события без сохранённого `rewarded`. При такой неполноте история требует отдельного разбора: автоматического исправления данных нет.
3. Сохраняет закрытый снимок установленного каталога в `sl_private.quiz_catalog_before_019()` с отзывом публичного доступа; при существующем снимке отказывается его перезаписывать.
4. Меняет только `lesson:lesson-1`: `count=20`, прежний `reward=35`, новые `start_questions` и объединение старых/новых ключей ответов. Guard проверяет сохранность каждого прежнего контекста, награды и ответа. У остальных уроков/режимов всё прежнее.
5. Не меняет event writer. Его существующий контракт 014 уже проверяет точное множество `start_questions`. Поэтому новая сессия обязана содержать 20 новых ID, а существующая 13-вопросная сессия продолжает оцениваться по сохранённым старым ID.
6. Через точные, однократные текстовые якоря `pg_get_functiondef` обновляет существующий `sl_get_progress`, сохраняя сигнатуру, owner, ACL, SECURITY DEFINER и search_path. Добавляет capability `alphabet_final_v1` и вычисляемый результат нового банка только из завершённых доверенных сессий данного пользователя с точным множеством 20 новых ID. Лучший результат выбирается по correct/started_at; признак награды берётся из прежнего общего ledger. При отсутствии новых попыток исходный snapshot сохраняется.
7. Меняет private manifest: lesson-1 — 20; остальные ID/категории/числа вопросов прежние. Активных вопросов уроков стало 518; 511 исходных исторических вопросов сохранены в источниках, из них 13 старых lesson-1 доступны в архиве.

Нет DML пользовательских таблиц, изменения Auth/схемы IndexedDB, удаления сессий, событий, результатов, XP или ревизий. Изменение reader проверено статически по исходнику; синтаксис/выполнение PostgreSQL на реальном сервере не проверялись. Это явно остаётся этапом будущего согласованного staging.

Предложение 018 остаётся архивным предложением для предыдущего этапа главы (13 вопросов, только manifest). Оно не является конечным выпуском этого задания. Не редактировать уже применённые миграции и не применять 018 как самостоятельный конечный релиз. Фактическую историю установленного Supabase нужно выяснить read-only перед выбором последовательности выпуска.

## Клиент и восстановление

Для гостя новый тест работает локально. Аккаунт должен иметь прежнюю capability `quiz_rewards_v1` и новую `alphabet_final_v1`. При её отсутствии запуск блокируется локализованным сообщением без создания новой сессии или событий. Это предотвращает отправку нового банка старому writer/catalog, но не заменяет синхронизацию manifest.

Стабильные option ID передаются на сервер независимо от языка и перемешивания вариантов. Снимок попытки сохраняет новую метаинформацию, локализованные объяснения, reading context, ссылки на правила и порядок вариантов. Старые снимки без этой метаинформации продолжают работать. Смена языка, возврат к правилу и перезагрузка не теряют ответ или текущий индекс.

Гостевой общий ledger также остаётся единым; учитывается существующий `completed` и прежний `rewarded`. Новая запись результата отделена от старого лучшего 13/13. Историческое прохождение не превращается автоматически в новый результат 20/20.

## Очереди и CONTENT_VERSION_MISMATCH

Проверены две разные ситуации:

- **Старый старт уже подтверждён сервером.** В IndexedDB сохранена `applied` квитанция `session_start`. Повторный enqueue находит эту квитанцию до сравнения версии. После согласованной смены версии попытка продолжает использовать ту же серверную сессию, прежние ID и UUID/тело события/квитанцию; последующие события создаются на актуальной версии. Тест модели подтверждает завершение старых 13 вопросов и новую 20-вопросную попытку с одной суммарной наградой.
- **Событие старой версии ещё не подтверждено.** Его `contentVersion`, UUID и `eventJson` не переписываются. Writer сохраняет блокировку несовместимости вместо потери события. Подготовленное предложение не разрешает автоматически отправку любого старого офлайн-события и не очищает очередь.

До выпуска нужно дать старому клиенту отправить очередь и подготовить отдельно согласованный переходный путь для оставшихся офлайн-устройств/неподтверждённых событий. Простое ожидание или очистка кэша не доказывают, что таких событий нет. Нельзя заявлять, что одна миграция решает все межверсионные очереди.
