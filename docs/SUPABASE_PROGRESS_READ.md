# Облачный прогресс: отдельный снимок для проверки

На этом этапе авторизация уже проверена владельцем на реальном Supabase.
Новый вызов RPC при разработке проверен только с моками; реальных RPC-запросов
в проект Supabase разработчик не выполнял. Деплой и SQL-миграции не выполнялись.

## Поведение

`app.js` запускает `SVProgress.initialize()` при загрузке приложения.
`supabase-progress.js` подписывается на существующий `SVAuth`, а после входа,
подтверждения email или восстановления сессии вызывает
`SVRpc.getProgress({expectedUserId})`. Это существующий адаптер `sl_get_progress()`:
он проверяет пользователя через Auth и закрепляет JWT за конкретным запросом.
Прямых запросов к таблицам и новой системы Auth нет.

Проверяются `revision` (безопасное целое >= 0), `content_version` (непустая строка
до 100 символов), `state` и ожидаемые типы его списков, счётчиков, повторений,
активности, настроек и профиля. Некорректный ответ отклоняется целиком.
Версия контента пока проверяется по формату, без решения о совместимости с
локальными материалами: это потребуется до применения облачного состояния.

Снимок — отдельная неизменяемая копия в памяти модуля. Он не записывается в
localStorage и не присваивается учебному `state`. При выходе или смене аккаунта
снимок сбрасывается; запоздавший ответ предыдущего сеанса входа отбрасывается.
Локальные данные аккаунта, `sv-guest-v2` и резервные копии не изменяются.

На один сеанс входа выполняется одна попытка чтения. Повторное открытие кабинета,
повторные события SIGNED_IN и TOKEN_REFRESHED не создают дополнительных запросов.
Ошибка не вызывает автоматических повторов. Новый вход или перезагрузка страницы
начинают новую попытку. Нет вызовов `sl_apply_event()` и автоматического импорта.
Существующая SQL-функция `sl_get_progress()` сама создаёт пустую запись
`sl_accounts`, если её ещё нет, и берёт блокировку для согласованного снимка;
начисления XP и импорта этот вызов не выполняет.

Ошибка выводится через существующее уведомление. Диагностика содержит безопасный
код и пояснение, без сырых сообщений сервера, деталей запроса, JWT или профиля.
При ошибке пользователь остаётся в аккаунте с прежним локальным прогрессом.

## Проверка в локальном браузере

1. Перезапустить `python3 server.py` — список доступных статических файлов
   расширен новым модулем. Открыть **http://127.0.0.1:8765/#profile** и обновить
   страницу. Для локальной диагностики подходят также localhost и IPv6 loopback.
2. Войти или дождаться восстановления существующей Auth-сессии.
3. Открыть DevTools → Console и выполнить:

   ```js
   SVProgressDebug.status()
   ```

   Ожидаемые поля:

   ```js
   {
     status: 'ready',
     attempts: 1,
     revision: 0,
     content_version: '...',
     knownWords: 0,
     xp: 0,
     errorCode: null,
     message: null,
     receivedAt: '...'
   }
   ```

   Значения в примере условные. Для пустого облачного аккаунта нули нормальны:
   локальное обучение на этом этапе в облако не передаётся. `loading` означает,
   что запрос ещё идёт. При `error` смотрите `errorCode` и `message`.
4. Для явной повторной попытки **после ошибки**:

   ```js
   await SVProgressDebug.retry()
   ```

   Если запрос ещё выполняется, используется та же попытка. Если снимок уже
   получен, новый запрос не отправляется. Без аккаунта возвращается `idle`.
5. В DevTools → Network отфильтровать `sl_get_progress`. Несколько раз уйти из
   кабинета и вернуться: число запросов не должно увеличиться. При обычном
   чтении также будет Auth-запрос проверки пользователя. Запросов
   `sl_apply_event` и `sl_import_progress` быть не должно.

`SVProgressDebug` существует только на loopback HTTP(S), отсутствует на GitHub
Pages и возвращает лишь сводку, без user ID, email, токенов или полного state.

## До безопасной синхронизации

- Проверить реальный RPC и его диагностику в браузере: пустой/непустой аккаунт,
  сбой сети, выход во время запроса и повторный вход.
- Определить правила совместимости content_version и применения облачного снимка.
- Спроектировать явный выбор источника прогресса и отдельный согласованный импорт
  с резервной копией, без автоматического смешивания гостевых данных.
- Подключать записи отдельно: стабильные event ID, expectedRevision, обработка
  конфликтов, повторов, офлайн-очереди и смены аккаунта.
