# Первый этап записи прогресса через RPC

Запись **выключена по умолчанию**. Включается только на HTTP(S) loopback
(`localhost`, `127.0.0.1`, `[::1]`) отдельным флагом браузера. На GitHub Pages
этот флаг не разрешает запись. Настоящий Supabase в рамках реализации не проверялся.

## Файлы и поведение

- `supabase-progress.js`: очередь, проверка совместимости, ревизии и применение
  проверенных серверных снимков в существующий `state` через callback.
- `app.js`: обработчики «Знаю» и избранного, запрет локального начисления XP
  в тестовом облачном режиме, сообщения о состоянии.
- `supabase-client.js`: статус разрешения записи делегирован `SVProgress`.
- `tests/supabase-preparation.cjs`: автоматические проверки на моделях RPC,
  IndexedDB и Web Locks, включая существующие проверки Auth/чтения.
- Этот документ: включение, ручная проверка и ограничения.

Используются существующие `SVAuth`, `SVSupabase`, `SVRpc.getProgress()` и
`SVRpc.applyEvent()`. Единственный писатель учебного прогресса — `sl_apply_event`.
SQL, контент, изображения и дизайн не менялись; импорта и деплоя нет.

Для гостя продолжается обычное локальное обучение. В облачном тестовом режиме
для вошедшего аккаунта доступны только `favorite_set` и `mark_known`.
Остальные изменения прогресса блокируются до выполнения локальной мутации.
Язык интерфейса можно менять локально, без отправки `settings_update`.

## Устройство очереди

Отдельная база IndexedDB `sv-cloud-events-v1`, версия 1:

- `events`: автоинкрементный порядок, владелец `userId`, UUID `eventId`,
  неизменная строка `eventJson`, версия контента, ожидаемая ревизия, статус.
- `baselines`: точные исходные байты локального состояния аккаунта,
  проверенного перед переходом на облачный источник истины.

Сначала завершается транзакция IndexedDB, затем возможен сетевой запрос.
UUID создаётся один раз через `crypto.randomUUID()`. В JSON только `type`,
`occurred_at` (ISO UTC с явным `Z`), IANA `timezone`, `data.word_id` и для
избранного `data.value`. Клиент не передаёт XP или параметры повторений.
При повторе неизменны UUID и `p_event`; `p_expected_revision` может измениться
после подтверждённого конфликта. Токенов в очереди нет.

Web Lock `sv-cloud-events:<userId>` сериализует создание и отправку событий
во всех вкладках одного origin. Если IndexedDB/Web Locks недоступны,
запись останавливается. Вкладки другого origin (включая другой порт или
`localhost` вместо `127.0.0.1`) имеют отдельные очереди; между ними работает
серверная проверка ревизий.

При успехе сохраняется статус `applied`, а UI получает проверенный серверный
снимок. Записи сохраняются как квитанции, не удаляются. Потеря ответа после
успешной записи приводит к повтору того же UUID: сервер возвращает `duplicate`.
Подтверждённое событие не начисляется локально.

Повторы выполняются после постановки в очередь, восстановления связи,
возврата фокуса, входа и загрузки страницы; для активной очереди/сессии есть
таймер 15 секунд. Если страница загрузилась без связи и первый read не удался,
событие `online` или возврат фокуса повторит чтение и возобновит очередь.
В закрытом браузере фоновой отправки нет.

Каждая операция проверяет ID и поколение авторизации. Запоздавший ответ старой
сессии не применяется. Запрос привязан существующим RPC-адаптером к проверенному
JWT владельца. При смене аккаунта его очередь остаётся на месте и ждёт входа
именно этого пользователя. Уже отправленный до выхода запрос может завершиться
на сервере от имени исходного аккаунта; его повтор безопасен.

При `40001` читается свежий прогресс. Для `mark_known` повторяется тот же UUID
и JSON с новой ревизией (не более двух попыток за один проход).
Для `favorite_set` старое намерение получает статус `conflict` и останавливает
дальнейшую отправку. Даже конфликт по несвязанному изменению требует проверки.
Автоматического переноса старого избранного на новую ревизию нет.
Ошибки валидации RPC сохраняют событие в статусе `blocked`.

Перед применением облака разрешены только отсутствующий/пустой локальный
учебный прогресс либо точно совпадающий с облаком. Непустое имя должно совпадать,
локальная фотография вызывает остановку. Настройки языка/уровня не импортируются.
После первой проверки исходные байты локального аккаунта сверяются перед
следующими операциями. Изменение этих байтов другим кодом останавливает запись.
Проверка консервативна: порядок списков тоже учитывается. Гостевой ключ не
читается для перехода; исходные аккаунтные данные и резервные копии не меняются.

## Диагностика загрузки и очереди через Chrome Console

`status().content_version` — версия учебных материалов, а не JavaScript.
В старом модуле экспортировались только `status`, `retry`, `preview`.
В текущем исходнике очередь уже была экспортирована, но URL оставался `?v=1`,
а RELEASE Service Worker — от предыдущего изменения интерфейса. Старый код
в открытой вкладке либо кешированная копия могли поэтому выглядеть актуальными
по версии материалов. По одному `status()` определить источник старых байтов нельзя.

Теперь URL модуля и RELEASE обновлены. На loopback Service Worker получает
shell-файлы с `cache: no-store` без offline fallback к старому коду; вне loopback
сохраняется прежняя поддержка offline. `server.py` уже читает файлы с диска на
каждый GET, игнорирует query при выборе файла и возвращает JS с правильным MIME
и `Cache-Control: no-cache`. Регрессионный HTTP-тест проверяет именно эти байты.

Чтобы обновить уже открытую старую вкладку, в Chrome DevTools → Application →
Service Workers включить **Bypass for network**, в Network — **Disable cache**,
затем перезагрузить страницу. Ничего не очищать через Clear site data.
Если локальный сервер недоступен, сначала запустить его из этого проекта.
Убедиться, что origin совпадает: порт и `localhost`/`127.0.0.1` имеют значение.

```js
Object.keys(SVProgressDebug);
// status, retry, preview, moduleVersion, diagnostics, queue, flush, acknowledgeConflict
SVProgressDebug.moduleVersion; // '2026-10-18-queue-debug-1'
const d = await SVProgressDebug.diagnostics();
d;
console.table(d.queue.events);
await SVProgressDebug.queue();
```

В Network проверить URL `supabase-progress.js?v=2026-10-18-queue-debug-1`,
статус 200, `Content-Type: text/javascript`, `Cache-Control: no-cache` и наличие
`moduleVersion`/`queue:queueStatus` в Response. После загрузки нового worker
можно снять Bypass/Disable cache и повторить перезагрузку. Если экспорт снова
старый, проверить URL страницы, каталог и процесс сервера; отключённый SW и HTTP
без кеша позволяют отличить не тот сервер от кешированной копии.

`diagnostics()` показывает загруженную версию и URL модуля, `flag` (текущее
значение localStorage), `writeEnabled` (значение на момент загрузки),
`reloadRequired`, наличие Web Locks, URL управляющего Service Worker и очередь.
Ни токены, ни ID пользователя, ни исходный прогресс в отчёт не включаются.
`queue()` и `diagnostics()` не запускают RPC, отправку, создание/обновление базы
или изменение флага. Существующие события текущего аккаунта видны даже при
выключенной записи; без текущего аккаунта список пуст.

`queue.storage.status`: `ready` — база прочитана, `absent` — ещё не создана,
`unavailable` — API отсутствует, `unsupported` — браузер не поддерживает безопасное
перечисление баз, `blocked`/`error` — чтение не удалось. Диагностика открывает
только существующую базу, использует readonly-транзакцию и закрывает соединение.
IndexedDB также доступна в Application → IndexedDB → `sv-cloud-events-v1` →
`events`/`baselines`; для обновления дерева использовать Refresh, без удаления базы.

Флаг разрешает запись только при точном значении `enabled` на HTTP(S) loopback.
Он читается один раз при загрузке; `reloadRequired: true` означает, что значение
изменили после загрузки. Для безопасного осмотра достаточно команд выше.
**Включение флага и перезагрузка могут автоматически отправить уже существующие
pending-события.** `flush()` также запускает отправку; это не команда диагностики.
В рамках исправления флаг в пользовательском браузере не включался и события
в настоящий Supabase не отправлялись.

## Включение для ручной проверки

1. Запустить `python3 server.py`; открыть `http://127.0.0.1:8765/`.
   Использовать тот же origin, где проверяли вход и пустой прогресс.
2. Войти. Пока запись выключена, проверить `SVProgressDebug.status()`:
   `ready`, версия `static-afaa62b7426e09a7`. Для сравнения без импорта:
   `SVProgressDebug.preview()` (гость исключён).
3. В DevTools Console выполнить:

   ```js
   localStorage.setItem('sv-cloud-write-dev-v1', 'enabled');
   location.reload();
   ```

4. После загрузки проверить:

   ```js
   SVProgress.writeEnabled;             // true
   SVProgressDebug.status();            // ready, совпадающая версия
   await SVProgressDebug.queue();       // ready: true, error: null
   ```

Если появился `LOCAL_PROGRESS_CONFLICT`, остановиться и сохранить конфликт
для отдельного разбора. Не очищать localStorage или IndexedDB ради обхода
проверки. Гостевой прогресс не переносится.

Для отключения записать `disabled` вместо `enabled` и перезагрузить **все**
вкладки этого origin. Флаг читается при загрузке. Существующая очередь останется
для следующего включения; флаг не отменяет уже отправленный запрос.

## Одно слово в настоящем Supabase

1. Открыть словарь, выбрать слово, например «arbeta» (`v-arbeta`).
   В Network включить Preserve log, отфильтровать `sl_apply_event`.
2. Нажать «Знаю» один раз. До ответа сервера XP и число слов не меняются.
3. В реальном запросе проверить `p_event.data.word_id`, UUID, `occurred_at`,
   `timezone`, `p_expected_revision`; полей XP быть не должно.
4. В ответе проверить `duplicate: false`, `progress.state.known` содержит ID,
   `progress.state.xp` вырос ровно на 8 для нового слова, ревизия выросла на 1.
   При исходных нулевых данных ожидаются XP=8, known=1, revision=1.
5. `await SVProgressDebug.queue()` показывает `applied`. Перезагрузить страницу:
   новый реальный `sl_get_progress` должен вернуть то же слово и XP=8.
   Убедиться, что UI показывает эти результаты.
6. Добавить звезду, дождаться `applied`, затем убрать и снова дождаться ответа.
   Избранное меняется, XP остаётся прежним. Повторно нажать «Знаю»:
   сервер может обновить расписание повторений и ревизию, XP остаётся 8.
7. Для доказательства идемпотентности повторить **тот же** запрос из Network
   через Replay XHR / повтор fetch в DevTools, сохранив UUID, JSON и ревизию.
   Ожидается `duplicate: true` и отсутствие дополнительного XP. Не публиковать
   скопированный запрос: он содержит заголовки авторизации.
8. В DevTools временно включить Offline, нажать новое «Знаю», убедиться в
   `pending`, перезагрузить, вернуть Online. Проверить `applied` и серверный XP.
   Выйти/войти; проверить, что результат пришёл из нового `sl_get_progress`.
9. Повторить изоляцию с другим тестовым аккаунтом: его состояние и очередь
   не должны содержать первое событие.

Это инструкция ручной проверки, а не отчёт о её выполнении.

## Проверка конфликта избранного

Второе устройство либо отдельный origin открывает тот же аккаунт. Пока первая
страница Offline, поставить избранное в её очередь. На втором устройстве
изменить прогресс, затем вернуть первой странице связь. Ожидаются `40001`,
свежий `sl_get_progress`, статус `conflict` и отсутствие применения старого
избранного. Проверить актуальную звезду в UI.

После осознанной проверки снять старое намерение с отправки:

```js
const q = await SVProgressDebug.queue();
// Выбрать проверенный eventId из q.events со статусом conflict.
await SVProgressDebug.acknowledgeConflict('проверенный-eventId');
```

Событие остаётся в базе со статусом `cancelled`. При необходимости заново
нажать звезду в UI: это новое пользовательское намерение с новым UUID.
Для локального конфликта прогресса автоматического разрешения нет.

## Автоматическая проверка и остающиеся ограничения

`node --test tests/supabase-preparation.cjs` — проверки на моках RPC и моделях
IndexedDB/Web Locks: Auth, отключённая запись, UI, избранное/«Знаю», XP,
потерянный ACK, offline/reload/online, два аккаунта, повторный вход, две вкладки,
конфликт ревизий, версия материалов, несовместимый локальный прогресс и ошибка
записи очереди. Это не реальный браузер и не тест настоящей PostgreSQL.

`python3 scripts/check_supabase_manifest.py` проверяет версию и ID материалов
по существующей миграции. SQL не менялся.

Перед подключением всех тренировок нужны ручная проверка в настоящем Supabase,
проверка нативных IndexedDB/Web Locks в целевых браузерах, протокол очереди
учебных сессий/ответов и восстановления сессий. Также остаются полноценный UI
разрешения конфликтов, политика хранения старых квитанций и получение облачного
снимка при первом запуске без интернета. Пока нет облачного офлайн-кэша для UI:
после offline reload показывается сохранённое локальное состояние до успешного
чтения сервера, новые аккаунтные действия до проверки снимка не принимаются.
Старые данные не импортируются и не удаляются.

  отдельная временная SQLite, без подключения к Supabase.
- `node --check` для изменённых JS и `git diff --check`: успешно.

Настоящий браузер с нативной IndexedDB и облачный `sl_apply_event` в этом запуске
не проверялись. Флаг записи в пользовательском браузере не включался.
