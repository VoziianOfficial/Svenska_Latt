# Svenska Lätt — технический аудит мобильной версии, 9 ноября 2026

Изменения подготовлены локально. Commit, push, merge, публикация и SQL в рабочем Supabase не выполнялись. Учебный контент, фотографии, Hero, формулы XP, пользовательские хранилища и события не изменялись/не очищались.

**Точная причина сообщения на конкретном iPhone пока не установлена.** Входящий материал содержит описание гостевого режима и 11/12, но не содержит сетевого журнала, доступа к устройству или самой фотографии. Нельзя выдавать один из воспроизведённых ниже сценариев за подтверждённую причину на телефоне.

## Опубликованная версия и запросы

Проверен https://voziianofficial.github.io/Svenska_Latt/. До правок опубликованные `index.html`, `app.js`, `atelier.js`, `sw.js` совпадали с локальным checkout. 19 подключённых CSS/JS доступны по HTTP 200. Закреплённый SDK Supabase 2.118.0 также отвечает 200. Хэши и статусы: `reports/mobile-qa/public-assets.json`. Это проверка сервера, а не содержимого Cache Storage на iPhone.

Публичный Supabase проверен без входа и записи данных, 9 ноября около 21:43 Europe/Stockholm:

| Запрос | Результат | Что доказано |
| --- | --- | --- |
| `GET /auth/v1/health` | 200 | Auth доступен в момент проверки; текущая недоступность paused не воспроизведена |
| `POST /rest/v1/rpc/sl_get_progress`, `{}`, public key, без JWT пользователя | 401, SQLSTATE 42501, `permission denied for function sl_get_progress` | Функция существует и гостевой вызов запрещён; это ожидаемая защита |

Последний запрос выполнен аудитором отдельно. **Гостевой интерфейс его не отправляет.** Это не запрос, установленный как источник ошибки пользователя. Доступ authenticated, RLS конкретного аккаунта, refresh настоящего JWT, `sl_apply_event` и фактически применённые миграции рабочего проекта без тестовой сессии не подтверждены.

В опубликованном коде `cloudAccount()` зависит от `user`, а `user` заполняется из SVAuth. `renderProgressUX()` показывает именно текст «Не удалось сохранить изменения. Попробуй ещё раз.» с «Повторить отправку» при облачной ошибке. При `user === null` эта ветка не выполняется. SDK/Auth outage у гостя показывает другое сообщение и другую кнопку. Прогресс 11/12 не доказывает авторизацию.

Плашка может означать не только неудачный запрос: `CONTENT_VERSION_MISMATCH`, `LOCAL_PROGRESS_CONFLICT`, отсутствие Web Locks или IndexedDB останавливают запись до `sl_apply_event`. Клиент ожидает `static-1750f0ad07cce4c4`; старый серверный manifest — проверяемая гипотеза, не установленный факт. Наличие файла миграции 017 в Git не подтверждает её применение.

## Исправления и доказательства

| Проблема | Причина и воспроизведение | Исправление |
| --- | --- | --- |
| Следующий клик карусели поглощается после drag | `dragged` оставался true после ухода указателя за пределы; touch/pen pointerdown не сбрасывал его, keyboard click тоже подавлялся. Воспроизведено на обработчиках в Node | Сброс для каждого нового жеста; keyboard activation с detail=0 разрешён; завершающий клик настоящего drag по-прежнему подавляется |
| Вертикальный жест на карусели запрещён | CSS задавал `touch-action:pan-x`. Найдено статически; на физическом iPhone не проверено | `touch-action:auto` разрешает нативную прокрутку по обеим осям и zoom |
| Повреждённое гостевое сохранение могло перезаписываться | `readLocalState()` молча возвращал defaults после ошибки JSON, последующий `save()` записывал их поверх исходных байтов. Воспроизведено DOM-тестом | Блокировка записи при ошибке чтения; отдельная локальная плашка; повторное чтение без очистки |
| Нет локального восстановления при quota error | `localStorage.setItem` бросал исключение без постоянного локального статуса. Воспроизведён QuotaExceededError | Состояние остаётся в памяти вкладки; локальная ошибка и повторное сохранение без вызова SVProgress/RPC. До успешной записи вкладку нужно сохранять открытой |
| Необработанный IndexedDB blocked | У open отсутствовал onblocked; в модели он оставлял promise ожидающим | Ошибка QUEUE_STORAGE_BLOCKED и повторная попытка. Проверено моделью; это не доказательство такого события на реальном iPhone |
| Большая общая инструкция установки; не различался встроенный iOS браузер | Все iOS user agents получали одинаковые длинные два абзаца | Компактные визуальные шаги; Safari отдельно от встроенных/других iOS браузеров; переход в Safari с вариантом копирования адреса; RU/UK/EN/SV; размеры диалога учитывают safe area |
| Непонятно, какой вызов завершился ошибкой | Production RPC adapter не сохранял безопасный контекст сбоя | `SVRpc.diagnostics()` возвращает последний сбой: operation, stage=session/verify_user/rpc, разрешённый code, at. Без токенов, ID, email, тел событий и исходных текстов ошибок. Исторический сбой не означает текущую неисправность |

Нативный `beforeinstallprompt` сохранён: вызов в user activation, одноразовое использование, защита от повторного клика. Принятие prompt не объявляется фактом установки; кнопка скрывается только по appinstalled/standalone. UA-определение является эвристикой: встроенный браузер может маскироваться под Safari. Основной путь iOS соответствует [инструкции Apple](https://support.apple.com/en-eg/guide/iphone/iphea86e5236/ios).

В очереди не удаляются события, UUID и JSON при retry сохраняются. Исправление onblocked закрывает поздно открывшееся соединение, но не удаляет базу. Для ошибок версии материалов и занятого хранилища добавлены отдельные сообщения.

## Кликабельность и покрытие

Новые DOM-проверки вызывают реальные делегированные click-обработчики и проверяют результат, а не только наличие HTML:

- SFI A/B/C/D открывают соответствующий список; все 50 карточек уроков открывают собственный lesson ID.
- Все словарные модули открывают собственную тему после повторных render.
- Все 9 домашних направлений работают с клонированными карточками; cloneNode сохраняет data-атрибуты и делегирование. Потери обработчиков у этих клонов не обнаружено.
- Словарная карточка открывает нужное слово; guest favorite/known сохраняются и восстанавливаются из localStorage.
- Все 14 тренировок запускают нужный режим с вопросами.
- Нижняя навигация, drawer open/close, профиль, числа и переход к разделу шпаргалки выполняют нужное действие.
- Все 12 книжных обложек через существующий enhanceBooks открывают правильную книгу.
- Ссылки видео сохраняют HTTPS URL, target и noopener; внешние ролики не просматривались. Остальные существующие тесты проверяют облачные watched/undo, конфликты, reload, pending и независимость от XP.

Статически просмотрены pointer-events, z-index, декоративные слои, touch-action, preventDefault/stopPropagation, drag capture, cloneNode, повторный render, disabled/aria-busy. Глобальная кликабельность информационных карточек не добавлялась. Ручное повторение выученного слова остаётся намеренно disabled по существующему контракту 015/016; исправлены два устаревших тестовых ожидания, поведение приложения не менялось.

## Действия для установления причины на iPhone и в Supabase

1. Зафиксировать страницу, действие, Safari/встроенный браузер/PWA и состояние профиля. После обновления на проблемном устройстве прочитать безопасные `SVRpc.diagnostics()`, `SVProgress.status()` и `SVProgress.writeStatus()`. Не отправлять токены, session storage, сырые сетевые заголовки и event payloads.
2. Если guest и diagnostics=null, RPC не подтверждён: проверить локальную ошибку и версию ресурсов в Safari Remote Inspector. Не очищать site data и не удалять приложение до сохранения локальных результатов.
3. Если ACCOUNT + CONTENT_VERSION_MISMATCH, сравнить manifest с `static-1750f0ad07cce4c4`. Если 42501/PGRST202 — проверить функцию и ACL. Если 23514/SRS_INTERVAL_LIMIT — проверить определение ограничения и наличие ранее подготовленного cap.
4. В SQL Editor владелец может вручную выполнить `supabase/tests/mobile_qa_diagnostics.sql`: BEGIN READ ONLY, metadata/ACL/RLS/manifest/constraints/fingerprints, затем ROLLBACK; пользовательские строки не читаются.
5. По результату отдельно согласовать только необходимое серверное исправление. Уже существующие 012/013/017 нельзя применять вслепую или повторять весь набор. Pending UUID/body должны сохраниться; после исправления использовать штатный retry. Для expired JWT использовать штатное обновление сессии; не удалять auth storage как способ ремонта.
6. После разрешённой публикации провести физический iPhone-прогон перечисленных размеров/сценариев, затем authenticated acceptance на выделенном тестовом аккаунте. Сейчас эта часть не считается завершённой.
