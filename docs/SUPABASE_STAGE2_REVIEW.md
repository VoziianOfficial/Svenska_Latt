Bucket создаётся закрытым; существующий avatars вызывает ошибку вместо перезаписи. Реальные Storage API/размер/MIME ещё не проверены. |

Все пять миграций используют поддерживаемые возможности PostgreSQL, успешно
проверенные на установленном PostgreSQL 14.20. Это не проверка версии/конфигурации
облачного PostgreSQL. Не изменяют служебную схему Auth и не добавляют signup-trigger,
который мог бы блокировать регистрацию. Аккаунт появляется при первом RPC, а не
автоматически при создании auth.users.

Приватная схема sl_private не должна быть добавлена в Data API exposed schemas.
Public должна быть доступна Data API. RLS и отозванные права обязательны независимо
от настроек Data API. SECURITY DEFINER-функции не должны менять владельца на
authenticated/anon; SQL Editor использовать под postgres.

## Обнаруженные ограничения и возможные ошибки

1. **Frontend несовместим с новой схемой без адаптации.** Сейчас app.js всё ещё
   вызывает learning_progress. После применения новых таблиц нельзя просто
   заполнить supabase-config.js и ожидать рабочую синхронизацию.
2. **Recovery отсутствует в приложении.** Нет resetPasswordForEmail, обработки
   PASSWORD_RECOVERY и updateUser формы. Настройки панели — необходимая часть,
   но не готовая функция восстановления.
3. **Auth и router используют fragment.** В implicit-потоке возвращаются токены
   в #..., а сайт читает fragment как маршрут. Нужен утверждённый callback/порядок
   инициализации; app.js в этом этапе не менялся. PKCE требует code verifier и
   отдельной проверки перехода между браузерами.
4. **SQL Editor обходит клиентский RLS.** Подготовлены отдельные проверки через
   настоящий парольный Auth и JWT двух пользователей, без service_role.
5. **Storage-политики могут складываться через OR.** Даже правильная новая policy
   не закрывает доступ, открытый другой широкой policy. Аудит выводит ВСЕ политики
   storage.objects, не только четыре sl_avatar_*.
6. **Bucket при повторе не перезаписывается.** При already exists остановиться,
   не удалять bucket и не добавлять ON CONFLICT вручную.
7. **Старый SQL нельзя смешивать с новым.** Старая таблица блокирует первую миграцию;
   запуск старого SQL после новых миграций автоматически не запрещён. В инструкции
   отдельно зафиксирован запрет обоих порядков смешивания.
8. **История CLI и SQL Editor различается.** После Dashboard-применения CLI может
   считать файлы неприменёнными. repair допускается только после проверки полного
   фактического применения, не как способ скрыть ошибку.
9. **SMTP по умолчанию ограничен.** Письма на адреса вне команды могут не отправляться;
   для полноценной проверки нужен свой SMTP. Тестовые auto-confirm пользователи не
   доказывают доставку и обработку confirmation/recovery.
10. **Удаление Auth не удаляет файлы и не мгновенно отзывает JWT.** Сначала очистка
    файлов через Storage API/UI, затем Auth delete/cascade; отдельно тестировать
    старый access token. Не удалять storage.objects через SQL.
11. **HTTP-тест пишет фикстуры.** Он требует нового тестового проекта и двух новых
    пользователей, не делает автоматический сброс и не должен запускаться на данных
    учеников. Даже неудачный тест может оставить записи/файлы.
12. **Подписанная ссылка — временный ключ.** Человек с такой ссылкой может скачать
    файл без JWT до истечения срока. Это штатное поведение, а не нарушение RLS.
