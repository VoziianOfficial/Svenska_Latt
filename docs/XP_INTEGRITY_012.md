Дата: 18 октября 2026. **Подготовлено и проверено только локально. В реальном Supabase миграция не применялась; устранение уязвимостей на сервере не подтверждено.**

Полный SQL без сокращений: [202610180012_xp_integrity.sql](../supabase/migrations/202610180012_xp_integrity.sql).

## Остальные XP и связанные RPC

- `answer` — 0 XP и проверка ответа сервером для trusted quizzes; повтор question_index запрещён.
- `session_start`, `session_abandon` — 0 XP. Незавершённый тест нельзя закончить.
- `session_finish` — прежняя логика 010: точный порог `correct*5 >= total*4`, однократная выплата на `(user_id, quiz_id)`, лучший результат не уменьшается. Новый session UUID не создаёт новую квиз-награду. Random/untrusted practice — 0 XP.
- `book_read` — 20 XP при первом переходе к completed. Этот RPC не позволяет снять completed: `value` не входит в допустимые ключи. Повторные UUID не дают XP. Сохранено как отдельное достижение чтения; book quiz по-прежнему имеет отдельную награду.
- `unmark_known`, `mark_review`, `review_grade`, `favorite_set`, `profile_update`, `settings_update` — 0 XP.
- `sl_review_change` вызывает только `review_grade` для оценок; собственных выплат нет. `sl_study_*`, `sl_get_progress`, `sl_request_account_deletion`, avatar policies/helper — не начисляют XP.
- Прямые INSERT/UPDATE/DELETE клиентам на `sl_*` запрещены. `sl_private.review` меняет SRS, не XP, и недоступен клиентам.
- Старые определения 003/007 заменены определением 010, а затем 012. Они не являются дополнительными callable перегрузками. `SUPABASE_SETUP.sql` — отдельная legacy-схема, установку которой 001 блокирует; не запускать её вместе с этими миграциями.
- Гостевой localStorage не является доверенным серверным балансом. Закрытие клиентского импорта не позволяет превратить локальные счётчики в облачные XP. Гостевой интерфейс этим серверным патчем не изменяется.

Для нового аккаунта при текущем неизменном каталоге верхняя граница штатных выплат конечна: 1006 × 8 за слова + 12 × 20 за чтение + 3748 за 113 trusted quizzes = **12 036 XP**. Исторические балансы могут быть выше; 012 их не ограничивает и не списывает. Это не защита от ложного заявления «знаю слово» или просмотра публичных ответов, а защита от повторной выплаты за одно достижение.

## Сохранность и права

- Миграции 001–011 не изменены; проверены побайтово относительно HEAD.
- Миграция 012 транзакционна. На время изменения исторических резерваций берётся `SHARE ROW EXCLUSIVE` на accounts/lessons/quiz_results/imports; `lock_timeout=10s` приводит к откату при занятой установке.
- Не меняются XP, answered/correct, events, imports/snapshots, SRS, known/favorites, activity, study time, очереди, профиль, настройки или session history. В quiz results добавляются лишь недостающие исторические резервации; существующие best scores не уменьшаются.
- Сохранены account row lock, проверка revision, привязка к `auth.uid()`, проверка UUID/body и первоначальные квитанции старых событий. `rules_version='quiz-rewards-v1'`, capability и формат `quiz_result` остаются прежними.
- Новый public import wrapper — `SECURITY DEFINER SET search_path=''`, как и event RPC. EXECUTE явно отозван у PUBLIC/anon и выдан authenticated. Старый import implementation перемещён в `sl_private.import_progress_legacy`, EXECUTE у PUBLIC/anon/authenticated отозван, schema usage для клиентов не выдаётся. Только wrapper может делегировать безопасный `archive_only`.
- Таблицы, их RLS и owner policies не ослабляются. Account A не может указать B в event payload или изменить его данные. Изменение JWT subject в локальном тесте моделирует переключение аккаунтов; настоящий JWT/HTTP не проверен.

## Тесты

`supabase/tests/008_xp_integrity.sql` сначала воспроизводит прежние обходы в disposable-базе, создаёт снимки всех `sl_*` таблиц, применяет 012 и проверяет точную сохранность данных, права, новые правила, исторические receipts, archive-only и запрет promotions.

Регрессии после 012: 20 циклов видео и неверных карточек; повторные correct/unmark/mark; книга; нулевые награды остальных событий; stale revision, UUID/body mismatch; import injection разными UUID/hash, empty-only, archive retry/promotion; изоляция; 70/80/100%, лучший результат, random practice; **каждый из 113 trusted quizzes — правильные ответы без XP, первое завершение и повтор**.

`scripts/test_supabase_local.py` дополнен реальными параллельными соединениями: одинаковый UUID, разные UUID с конфликтом/rebase, unmark/relearn, mixed mark/flash, wrong flash, video true/false/true, book, два квиз-финиша и потерянный ACK. Отдельная БД устанавливает настоящие 001–011 **в числовом порядке**, затем создаёт предмиграционные данные и применяет 012 с теми же assertions. Никакой URL Supabase, CLI или credentials runner не принимает; PG-переменные окружения исключаются. Сервер PostgreSQL слушает только закрытый Unix socket.

## Риски и проверка перед реальной установкой

1. **На реальном Supabase не проверено.** Роли Auth/Storage локально — тестовые заглушки. Нужны отдельные authenticated HTTP/JWT/RLS проверки на настоящем disposable Supabase-проекте, затем отдельное разрешение на установку в рабочий проект. Этот документ не разрешает запуск SQL.
2. Все прежние балансы, включая ранее ошибочно начисленные XP, сохраняются. Исправляется будущая выплата; история не пересчитывается.
3. Новые `empty_only`/`independent` импорты больше не работают: клиенты получают `42501`. Архивы и исторические ACK остаются доступными. Доверенный механизм миграции старого локального прогресса потребует отдельного серверного дизайна; секретный ключ в браузер помещать нельзя.
4. У уже завершённых исторических уроков новая награда не появится; их исходный XP не изменится. Существующие результаты и best сохраняются.
5. Выполнять cutover с кратким прекращением входящих мутаций и завершением старых in-flight RPC. Старый выполняющийся код/уже отправленные запросы нельзя считать исправленными только потому, что DDL завершён. Не полагаться на блокировку таблиц как замену maintenance window.
6. Установку должен выполнять владелец функций/таблиц. Нужно проверить отсутствие schema drift, существование ровно сигнатур из 001–011, ACL и RLS в Dashboard. При lock timeout или ошибке транзакция должна откатиться; не обходить её частичным ручным выполнением.
7. Тестовые `supabase/tests/*.sql` содержат fixtures и вспомогательные definer-функции и **не должны устанавливаться в Supabase**. Для установки предназначен только файл миграции после отдельного согласования.
8. После согласованной установки проверить на отдельных аккаунтах повторное видео, wrong/correct flash, unmark/relearn, replay UUID, два устройства, три пороговых квиза и сохранение исторического XP/SRS. Не списывать XP основного аккаунта ради теста.
