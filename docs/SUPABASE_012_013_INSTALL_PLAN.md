## 1. До окна установки

1. Сверить project ref/окружение в Dashboard и CLI, владельца функций/таблиц и доступность проверенной резервной копии с процедурой восстановления. Не передавать пароль/ключ service_role в браузер или журналы. Нужны полномочия владельца объектов; реальные роли локальная заглушка не подтверждает.
2. В связанном CLI-проекте выполнить только проверку истории: `supabase migration list --linked`. Сопоставить точные версии 001–011 с файлами репозитория. Если фактически применённые вручную 001–011 отсутствуют в истории, сначала сверить схему и отдельно согласовать регистрацию **только подтверждённых версий**; не запускать старые файлы повторно и не отмечать неизвестную миграцию applied.
   Версии репозитория состоят из 12 цифр: сохранять их буквально, не дописывать секунды и не переименовывать 001–013. При ошибке форматирования дат в CLI проверять сами строки `version` в `supabase_migrations.schema_migrations` (если таблица существует), а не визуальные колонки дат:

   ```sql
   select version from supabase_migrations.schema_migrations order by version;
   ```

   Совместимость конкретной версии CLI должна быть проверена на staging. В текущем окружении CLI не установлен; его команды здесь не выполнялись. В [официальном исходнике repair](https://github.com/supabase/cli/blob/develop/apps/cli-go/internal/migration/repair/repair.go) версия разбирается как число; сама команда регистрации не исполняет statements миграции. Не использовать `migration repair` без явной версии: это другой, массовый сценарий исправления истории.

3. Убедиться в отсутствии schema drift: публичные RPC, сигнатуры/возвращаемые типы, владельцы, search_path, RLS/политики соответствуют проверенным 001–011. В текущей базе нет `sl_private.import_progress_legacy`; `public.sl_import_progress(uuid,bigint,uuid,jsonb,text)` существует. При ином состоянии остановиться: 012 не предназначена для повторного выполнения.
4. Сохранить `pg_get_functiondef('sl_private.review(uuid,text,boolean,timestamptz)'::regprocedure)`, ACL и владельца: это должен быть установленный capped helper, совпадающий с 013. Отдельно сохранить определения текущих event/import RPC и защищённый снимок quiz results для сравнения исторических резерваций.
5. Подтвердить изменение импорта как ожидаемое поведение: новые `empty_only`/`independent` получают `42501`, разрешён `archive_only` и ACK ранее применённых импортов. Это намеренное несовпадение поведения со старым сервером, а не полная обратная совместимость всех операций. Проверить соответствующий экран текущего клиента на staging; локальный гостевой прогресс не удалять.
6. Провести настоящий JWT/PostgREST/RLS smoke test на отдельном disposable Supabase/staging-проекте. Локальные тесты проверяют PostgreSQL, не PostgREST/Auth/Storage и не доставку схемы API.

## 2. Остановить мутации и снять исходный снимок

Остановить новые записи и дождаться завершения старых RPC, study commits и других фоновых writer-ов. Открытые вкладки и другие устройства могут продолжать отправлять запросы: одного закрытия страницы недостаточно. Нужен заранее согласованный способ ограничить входящие мутации; текущий интерфейс не доказывает наличие такого режима. Не менять RLS/ACL наугад.

Сохранить локальные pending-события с их исходными UUID/body: не очищать IndexedDB/localStorage и не пересоздавать события. После установки они должны получить прежний ACK либо пройти обычную revision-conflict/rebase обработку.

В SQL Editor рабочего проекта, в отдельном запросе, выполнить файл `supabase/checks/012_013_state.sql`. Он использует READ ONLY/REPEATABLE READ, не вызывает mutating RPC, выводит количества и fingerprints, каталог RPC, ACL/RLS и число недостающих исторических резерваций. Сохранить результат как **before-012**. Запрос сканирует таблицы; на большой базе возможен безопасный timeout 30s, требующий пересмотра способа сравнения, а не пропуска проверки.

Fingerprints — контроль случайных изменений, не резервная копия и не криптографическое доказательство. Пока writer-ы остановлены, количества и fingerprints позволяют сравнить всё содержимое таблиц без вывода персональных данных. Изменения тестовых аккаунтов выполнять только после сравнений.

В SQL Editor выполнить полный `202610180013_srs_interval_cap.sql`. Повторный CREATE OR REPLACE поверх ручного патча проверен локальными тестами; этот путь выбран для одинаковой процедуры на разных установках.

Снять **after-013** тем же read-only файлом. Все таблицы, включая `sl_quiz_results`, должны точно совпадать с **after-012**. Определение capped helper/ACL/владелец совпадают с установленным ручным патчем, интервал ограничен 365000, новые XP не начисляются. После успешного COMMIT и сравнения:

```sh
supabase migration repair 202610180013 --status applied --linked
supabase migration list --linked

```

Ожидаются remote записи всех 001–013 и отсутствие pending migrations. Если dry-run предлагает старые миграции или любые неожиданные изменения — остановиться и согласовать историю. Команды настоящего `db push`, reset, down, reverted, squash, удаления данных/хранилищ в этот план не входят.

Важно: наличие ручного hotfix не создаёт запись 013 автоматически; `CREATE OR REPLACE` из SQL Editor также не ведёт CLI-историю. Регистрацию выполнять только после проверки фактического состояния. Официальные основания: [история миграций Supabase](https://supabase.com/docs/guides/deployment/database-migrations), [migration repair](https://supabase.com/docs/reference/cli/supabase-migration-repair), [db push --dry-run](https://supabase.com/docs/reference/cli/supabase-db-push).

## Риски и условия остановки

- Тестовая PostgreSQL с заглушками Auth/Storage не заменяет версию/расширения реального Supabase и его HTTP/JWT/RLS acceptance.
- Без остановки writer-ов нельзя гарантировать отсутствие выполнения старого кода во время cutover или точное сравнение снимков. 10-секундный lock timeout 012 защищает от ожидания блокировок, но не заменяет окно обслуживания.
- Исторические XP сохраняются, даже если ранее были начислены ошибочно. Миграция закрывает будущие выплаты; она не исправляет старый баланс.
- Новые baseline импорты намеренно закрыты. Если перенос гостевого прогресса нужен как штатная возможность, требуется отдельное доверенное решение и согласованный UX, без переноса secret key в клиент.
- Если COMMIT прошёл, но acceptance не прошёл, держать мутации остановленными, сохранить журнал/снимки и готовить отдельное исправление. Не откатывать пользовательские данные, не восстанавливать уязвимый RPC, не отмечать миграцию reverted для вида; восстановление backup требует отдельного решения, поскольку может потерять новые данные.
- Общие блокеры публикации B2/B3: подтверждённые сведения о данных и завершённое удаление аккаунта; облачный профиль/фото/отметки контента. Полный браузерный/PWA/мобильный acceptance остаётся отдельным условием выпуска. Успех установки БД не означает готовность всего сайта.
