# Svenska Lätt — план развёртывания и реальных проверок Supabase

Подготовлено 17 октября 2026. Никаких операций с реальным проектом не выполнено.
Все действия ниже — для выполнения ПОСЛЕ отдельного подтверждения. На этом этапе
app.js, localStorage, пять миграций и старый SUPABASE_SETUP.sql не менялись.

## Что проверено и что ещё не доказано

Пять файлов сверены с актуальной официальной документацией Supabase. Используются
обычные возможности PostgreSQL и документированные Auth/Storage-контракты.
Обязательные зависимости приведены в отчёте `SUPABASE_STAGE2_REVIEW.md`.
Это проверка по исходникам и документации, а не утверждение, что удалённый проект
уже прошёл приёмку. Полный стек Supabase в этой среде не установлен.

Рекомендуемый первый запуск — новый ОТДЕЛЬНЫЙ тестовый проект с двумя специально
созданными пользователями. Данные настоящих учеников и их localStorage не нужны.
Тесты записывают фикстуры и не являются «только чтением» или автоматическим rollback.

## Порядок и точки подтверждения

1. Одобрить создание/выбор нового тестового Supabase-проекта и применение пяти
   миграций. До этого никаких удалённых команд, даже CLI dry-run/link, не выполнять.
2. После применения проверить read-only аудит, создать два тестовых аккаунта.
3. Отдельно одобрить тестовые HTTP-записи и загрузки аватаров в этот проект.
4. Запустить подготовленную приёмку; сохранить только PASS/FAIL, версии и настройки,
   без токенов, паролей, signed URL и полных ссылок из писем.
5. Отдельно проверить подтверждение email/recovery, затем выполнить согласованную
   очистку тестовых пользователей. Интеграция frontend требует следующего согласования.

Ни Project URL, ни publishable key не являются секретными серверными ключами;
их можно посмотреть в панели, но supabase-config.js пока заполнять не следует.
Пароль БД/тестового пользователя, access/refresh token, SMTP-пароль, personal access
token CLI и service_role/secret key в чат не присылать. Для SQL Editor пароль БД
не требуется. Терминал теста запрашивает только пароли фиктивных пользователей
локально через скрытый ввод, не пароль базы.

## Вариант A: SQL Editor — проще для первого применения

После подтверждения:

1. В панели выбрать именно новый тестовый проект и дождаться готовности Database,
   Auth и Storage. Записать project ref и версию PostgreSQL, не секреты.
2. SQL Editor → New query, роль `postgres`. Открыть файл
   `supabase/tests/010_remote_preflight.sql`, вставить целиком и Run.
   Он READ ONLY, но всё равно является операцией с реальным проектом.
3. Ожидания preflight:
   - auth.users, auth.uid(), storage.buckets, storage.objects существуют;
   - роли postgres, anon, authenticated, service_role присутствуют;
   - `no_legacy_progress` и `no_private_schema` = true;
   - списки существующих sl_* объектов и bucket avatars пустые;
   - доступные поля Storage совпадают с запросом;
   - любые существующие Storage-политики изучены: разрешения объединяются через OR.
   Если найдены старые данные или непонятные политики — остановиться, ничего не удалять.
4. Выполнить ЦЕЛИКОМ каждый файл, строго в этом порядке; каждый — отдельный запрос:
   1. `supabase/migrations/202610170001_core.sql`
   2. `supabase/migrations/202610170002_manifest.sql`
   3. `supabase/migrations/202610170003_progress_rpc.sql`
   4. `supabase/migrations/202610170004_import.sql`
   5. `supabase/migrations/202610170005_avatars.sql`
5. Каждый файл уже имеет BEGIN/COMMIT. При ошибке не продолжать и не исполнять
   отдельные «оставшиеся строки». Если соединение осталось в aborted transaction,
   выполнить ROLLBACK; затем выяснить причину. Ранее успешные файлы не повторять.
6. После пяти успешных файлов выполнить read-only
   `supabase/tests/011_remote_audit.sql` и проверить результаты по разделу ниже.
7. Записать для каждого файла имя, SHA-256, время, роль и результат. Применение через
   SQL Editor НЕ создаёт автоматически запись в CLI migration history.

Старый `SUPABASE_SETUP.sql` не выполнять ни до, ни после новых миграций.
Он не заменяет их и создаёт несовместимый старый контракт learning_progress.
Первая миграция обнаруживает эту таблицу и останавливается ДО установки новой схемы.
Применение старого SQL ПОСЛЕ новых миграций этой защитой не блокируется: это отдельный
процедурный запрет, а не обещание автоматического предотвращения.
Не запускать bootstrap_local.sql или контрактные тесты с фиктивными SQL-вставками
auth.users в облаке. Реальные тестовые аккаунты создаются через Auth, не INSERT SQL.

## Вариант B: Supabase CLI — альтернативный путь

Команды ниже не выполнены. CLI может запросить секреты локально в терминале;
их не передают аргументами команд, не сохраняют в git и не присылают в чат.
Выберите этот путь ИЛИ SQL Editor для первичной установки, а не оба подряд.

После одобрения, из корня проекта:

```sh
supabase --version
supabase init
supabase login
supabase link --project-ref YOUR_TEST_PROJECT_REF
supabase migration list --linked
supabase db push --linked --dry-run
```

`supabase init` нужен только если ещё нет supabase/config.toml; существующую
конфигурацию не перезаписывать. login/link/dry-run обращаются к Supabase: это не
«офлайн-проверка». Ref должен быть явно сопоставлен с новым тестовым проектом.
Не использовать --include-all/--include-seed/--include-roles или --yes.

Dry-run должен перечислить ровно пять подготовленных миграций в правильном порядке:
версии `202610170001` … `202610170005`. Имена имеют числовые уникальные версии;
если установленный CLI не принимает их или выводит другой набор, остановиться,
не переименовывать файлы молча. Версия CLI пока не проверена в этой среде.
Dry-run показывает список миграций, а не доказывает компиляцию всех SQL/RLS в проекте.

После проверки списка и подтверждения применения:

```sh
supabase db push --linked
supabase migration list --linked
```

Это применение схемы БД, не git push и не деплой сайта. Выполнять только с явным
подтверждением. Никогда не использовать `db reset --linked`/remote reset: он удаляет
объекты, что не входит в этот план.

Если миграции уже применены через SQL Editor, НЕ делать db push поверх них.
Сначала проверить совпадение SQL/контрольных сумм и фактических объектов, потом
отдельно согласовать только регистрацию уже выполненных версий:

```sh
supabase migration repair 202610170001 202610170002 202610170003 202610170004 202610170005 --status applied --linked
```

`migration repair` меняет историю, не исполняет SQL; её нельзя применять для сокрытия
ошибки или неполного выполнения файла. В этом этапе команда не выполнялась.
CLI-путь не требует публикации сайта или изменения app.js.

## Ожидания read-only аудита

- Ровно семь ожидаемых таблиц; каждая: rls_enabled=true, member_select=true,
  member_any_write=false, anon_any_access=false.
- На каждой таблице только own_read/SELECT для authenticated с проверкой auth.uid().
- Четыре публичных RPC: SECURITY DEFINER, владелец postgres, search_path пустой.
  anon_execute=false, member_execute=true.
- sl_avatar_access — SECURITY INVOKER, не definer; member_execute=true,
  anon_execute=false. Он возвращает boolean и читает accounts через RLS клиента.
- У всех sl_private-функций member_execute=false, anon_execute=false;
  нет USAGE private schema для anon/authenticated.
- Bucket avatars: public=false, file_size_limit=1048576, MIME только JPEG/PNG/WebP.
- На storage.objects RLS включён и ровно четыре ожидаемые sl_avatar_* политики
  плюс только заранее изученные политики других bucket. Нет глобального USING(true)
  или иных широких правил, которые открывают avatars через OR.
- FK аккаунта указывает на PK auth.users(id) с ON DELETE CASCADE; ссылки на сессии
  включают user_id. Таблица learning_progress отсутствует.

SQL Editor обычно работает как postgres и может обходить RLS. Не считать успешный
SELECT из этой панели проверкой запрета для чужого пользователя. Это только аудит.

## Реальные тесты RLS/RPC/Storage

Подготовлен `scripts/test_supabase_remote.py` без внешних Python-зависимостей.
По умолчанию он не делает сетевых запросов:

```sh
python3 scripts/test_supabase_remote.py
```

После ОТДЕЛЬНОГО подтверждения реальных тестовых записей:

1. Authentication → Users → Add user/Create user: создать двух НОВЫХ фиктивных
   пользователей A и B с разными email/UID и известными вам паролями. Для теста RLS
   можно auto-confirm этих двух пользователей. Это не тест доставки email!
2. Не использовать реальные учебные аккаунты. Скрипт требует revision=0 и пустые
   таблицы прогресса; после неуспешного запуска фикстуры могут остаться. Не сбрасывать
   их автоматическим DELETE ради повторного запуска — сначала изучить результат.
3. В API Keys скопировать только `sb_publishable_...` и Project URL.
4. Локально запустить:

```sh
python3 scripts/test_supabase_remote.py --run
```

5. Ввести URL/публичный ключ, точное подтверждение project ref и пароли A/B в локальном
   терминале. Скрипт получает настоящие токены через Auth, проверяет /auth/v1/user,
   создаёт отдельную вторую сессию A2. SQL Editor postgres и service_role не используются.

| Проверка | Ожидаемый результат |
|---|---|
| Без JWT + public key | таблицы и RPC запрещены, 42501 |
| Один UUID, две сессии A | XP +8 один раз, ревизия +1, duplicate=true при повторе |
| Тот же UUID, другое тело | 22023, состояние не изменилось |
| Одновременное изменение имени | один успех, один 40001, нет скрытой перезаписи |
| Два новых изученных слова | конфликт; после явного rebase оба сохранены, итого XP=24 |
| Урок/ответы/книга | score/XP рассчитывает RPC; повтор вопроса новым UUID — 23505 |
| Архив локального снимка | отдельная запись sl_imports без дополнительного XP |
| B читает строки A | [] во всех семи таблицах, при этом A видит свои заполненные строки |
| Прямые INSERT/UPDATE/DELETE | 42501, чужой прогресс не меняется |
| Аватар A | загрузка/чтение/обновление/удаление владельцем разрешены |
| B обращается к аватару A | чтение, обновление, загрузка в папку A и выдача signed URL запрещены |
| B пробует удалить аватар A | файл остаётся доступен A, даже если API удаления вернул [] |
| Public URL приватного файла | недоступен без подписанной ссылки |
| Signed URL от A | временно работает без JWT; это ожидаемое свойство ссылки-ключа |
| Неподходящий MIME / >1 MiB | Storage отклоняет, не 5xx |

Тест обрабатывает документированные и старые обёртки ошибок Storage; неизвестная
ошибка не считается PASS. При fail остановиться и посмотреть Logs API/Auth/Storage.
Не включать логирование access/refresh token и не сохранять полный signed URL.
Скрипт удаляет только свой успешно проверенный файл аватара через Storage API.
Он НЕ удаляет пользователей, не применяет миграции и не выполняет auto-rollback.
Фикстуры остаются в аккаунтах для проверки в панели.

План отдельной проверки удаления: после одобрения очистки убрать файлы A/B через
Storage UI/API, затем удалить ТОЛЬКО тестовых пользователей в Authentication → Users.
Read-only SELECT count(*) по их UUID во всех семи таблицах должен дать 0. Убедиться,
что другие пользователи не затронуты. Не удалять production storage.objects через SQL.
Если проверяется pending-delete RPC, сначала заморозить тестовый аккаунт и проверить
запрет новых записей/загрузок; дальнейшие файлы удаляет оператор панели/доверенный сервер.
Auth delete не мгновенно отзывает уже выданные JWT; проверка отзыва/истечения токенов
и отсутствие доступа к удалённым данным — отдельный пункт, не «JWT сразу невалиден».

## Email, восстановление и hash-маршрутизация

Настройки панели можно подготовить сейчас после подтверждения, но полный вход по
ссылкам и смена пароля в текущем приложении ещё НЕ готовы к приёмке.

1. Authentication → Sign In / Providers (название раздела может различаться) → Email:
   включить Email provider и Confirm email; пароль не короче текущих 8 символов.
   Не выключать подтверждение для настоящих пользователей ради теста RLS.
2. Authentication → Email / SMTP: настроить свой SMTP для произвольных адресов.
   Встроенная доставка ограничена адресами команды проекта и строгими лимитами;
   это может дать `Email address not authorized`, что не является ошибкой миграции.
3. Authentication → URL Configuration:
   - Site URL — точный корень реального сайта с HTTPS и полным подкаталогом;
   - Redirect URLs — точные разрешённые адреса возврата, без универсального production **;
   - локальный адрес добавляется отдельно только для теста.

Реальный адрес публикации в репозитории не задан. Не использовать имя проекта как
доказанный URL. Шаблон для GitHub Pages (заменить OWNER/REPO реальными значениями):

```text
Site URL:
https://OWNER.github.io/REPO/

Redirect URLs для текущего пути:
https://OWNER.github.io/REPO/
https://OWNER.github.io/REPO/index.html   (только если сайт действительно открывается так)
http://127.0.0.1:8765/                   (только локальный тест)
```

Текущий app.js задаёт emailRedirectTo как location.origin+location.pathname.
Поэтому корень `/REPO/` и `/REPO/index.html` — разные допустимые варианты; разрешать
только используемые. `#profile`, `#home` и другие маршруты НЕ добавлять в Site URL
и не использовать как Auth callback. У URL только один fragment, а implicit Auth
возвращает там #access_token=...&refresh_token=...; ошибки тоже могут прийти в hash.

Для следующего этапа предпочтителен отдельный реальный статический callback-файл,
например `/REPO/auth-callback.html`, который не запускает роутер до завершения Auth.
Он пока НЕ создан: добавить такой Redirect URL можно после утверждения его пути,
но направлять письма на несуществующий файл нельзя. Другой допустимый вариант —
изолировать callback на корневой странице и только потом запускать hash-роутер;
это потребует изменений app.js, запрещённых на этом этапе.

PKCE возвращает ?code=..., а не токены в hash, но требует обмена кода и сохранённого
code verifier в исходном браузере. Переход из письма в другой браузер/устройство
может не завершиться. PKCE сам по себе не добавляет форму восстановления пароля.
Выбор flow и поведения между устройствами должен быть принят при frontend-интеграции.

4. Email Templates: сохранить рабочие шаблоны Confirmation/Reset password с
   {{ .ConfirmationURL }} для стандартной ссылки проверки. Не заменять её просто
   на SiteURL: иначе email не подтверждается. Кастомные token_hash/RedirectTo-шаблоны
   требуют соответствующего обработчика, которого сейчас нет.
5. Будущий reset flow: resetPasswordForEmail(email,{redirectTo: точный callback}),
   обработка PASSWORD_RECOVERY/ошибок, отдельная форма, updateUser({password}),
   очистка чувствительного URL после обработки. В текущем app.js этих шагов нет.

Email-проверки после подготовки callback:

- Новый неподтверждённый пользователь не входит по паролю до подтверждения;
  письмо приходит на контролируемый ящик, ссылка возвращает на верный подкаталог.
- Просроченная и повторно использованная ссылки показывают понятную ошибку, не
  стирают progress/localStorage и не попадают в обычный hash-router.
- Recovery открывает форму нового пароля; новый пароль работает, старый больше нет.
- Проверить письмо в том же и другом браузере; описать ограничения выбранного flow.
- Отклонённый Redirect URL не превращается в открытый redirect; наблюдать реальное
  поведение Auth (ошибка или fallback на Site URL), не считать fallback успехом.
- Не сохранять полные callback URL со служебными параметрами в отчёт/скриншоты/чат.

## Возможные ошибки и действия

| Симптом | Что проверить |
|---|---|
| Legacy learning_progress exists | выбран старый проект/запущен старый SQL; остановиться, не удалять данные |
| schema/table/function/bucket already exists | повторный запуск или не пустой проект; сверить журнал применения |
| permission denied при миграции | роль SQL Editor/владение объектов; не выдавать PUBLIC права |
| PGRST202 / RPC not found | применена ли миграция, схема public в Data API, состояние schema cache |
| 42501 от пользовательского прямого DML | ожидаемый запрет; применять только RPC |
| 40001 | ожидаемый конфликт revision, нужен fresh snapshot и осознанное разрешение |
| 23505 при втором ответе | ожидаемая защита от повторного question_index |
| Invalid JWT / 401 | перепутан public key с пользовательским JWT, истёк токен или другой проект |
| Storage NoSuchBucket/NoSuchKey | проверить owner-positive запрос; отсутствие доступа может маскироваться как 404 |
| invalid MIME/EntityTooLarge | проверить лимит обработанного аватара 1 MiB и Content-Type |
| Email address not authorized/429 | SMTP/лимиты Auth, не права таблиц |
| Recovery письмо пришло, формы нет | frontend callback/recovery ещё не реализован, панель это не исправляет |

Никакие ошибки не исправлять отключением RLS, выдачей service_role клиенту или
созданием старой learning_progress ради текущего frontend. Первая интеграция сайта
должна использовать новый RPC-контракт после отдельного подтверждения.
