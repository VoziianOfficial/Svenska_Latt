# Предварительный просмотр переноса — 17 октября 2026

Добавлен `SVProgressDebug.preview()` в существующую диагностику локального
приложения. Интерфейс, дизайн, учебные материалы и SQL-миграции не менялись.
Импорт, отправка учебных событий и деплой не выполнялись. Реальные значения
учебного прогресса пользователя в этой проверке не читались и не изменялись:
JS-тесты используют искусственные данные. Дополнительно была предпринята
попытка запуска отдельного временного PostgreSQL без доступа к реальной базе.

## Где находятся данные

| Источник | Место | Поведение |
| --- | --- | --- |
| Текущий Supabase-аккаунт, локальное обучение | localStorage `sv-account-local-v1-<user.id>` | `save()` пишет только сюда после входа; при смене аккаунта читается его отдельный ключ |
| Гость | localStorage `sv-guest-v2` | Используется без аккаунта; при входе не копируется в аккаунт |
| Облако | Таблицы Supabase через `sl_get_progress()` | Проверенный снимок хранится отдельно в памяти `supabase-progress.js`; локальное обучение им не заменяется |
| Старые резервные копии | В частности `sv-cloud-backup-<userId>` | Не используются как автоматический источник; не изменяются |
| Незавершённая тренировка | sessionStorage `<ключ источника>:quiz-v1` | Отдельная для гостя и каждого аккаунта; RPC импорта её не переносит |
| Общие настройки устройства | `sv-language`, `svenska-latt-speech-speed`, `svenska-latt-swedish-voice` | Не являются доказательством принадлежности прогресса аккаунту |

В текущем frontend нет обращений к IndexedDB. Предпросмотр не открывает её,
не перечисляет чужие аккаунтные ключи и не обращается к старой SQLite-базе.
Фото профиля находится в `state.profile.avatar` как data URL, а не в облачном
`avatarPath`. Старые данные могут требовать отдельного определения владельца;
совпадения email недостаточно, чтобы связать старый источник с Supabase UUID.

## Как посмотреть сравнение

На обновлённой локальной странице `http://127.0.0.1:8765/#profile` войти в
**существующий аккаунт** и дождаться `SVProgressDebug.status().status === 'ready'`.
В DevTools Console:

```js
const preview = SVProgressDebug.preview();
console.table({
  localAccount: preview.account?.summary,
  cloud: preview.cloud
});
preview.account; // наличие источника, compatible, issues, warnings, differences
preview;         // revision, content_version, receivedAt и ограничения
```

Сводка содержит XP, число изученных слов (`known`), избранное (`favorites`),
завершённые уроки (`completed`), книги (`booksRead`), видео, ответы, верные ответы,
точность в процентах, число расписаний повторения, активные дни и дневную активность.
`differences` показывает `localOnly`, `cloudOnly` и `shared` для каждого списка.
Идентификаторы в отчёте — идентификаторы материалов. Профили, фото, email, UUID
пользователей, токены и полное исходное состояние не возвращаются.

По умолчанию гостевой ключ даже не читается. Для **отдельного просмотра гостя**:

```js
const separateSources = SVProgressDebug.preview({includeGuest: true});
console.table({account: separateSources.account?.summary,
  cloud: separateSources.cloud, guest: separateSources.guest?.summary});
```

Эта опция разрешает только чтение гостевого источника; согласия на объединение
или импорт она не означает. Гостевой прогресс не прибавляется к аккаунтному.
Отсутствующий аккаунтный ключ возвращает `absent`, повреждённый — `unreadable`
или `invalid`; гостевой источник не подставляется вместо него. Просмотр недоступен
без готового облачного снимка текущего сеанса. Выход и смена аккаунта немедленно
закрывают доступ к предыдущему снимку.

`preview()` синхронный: не вызывает RPC, не обновляет облачный снимок, не пишет
в хранилища и не создаёт готовое тело запроса импорта. Диагностика доступна
только на loopback HTTP(S). Снимок может устареть после получения — перед будущим
импортом потребуется новое чтение с проверкой пользователя и revision.

## Совместимость и обнаруженный блокирующий пункт

Проверка работает с **исходным JSON из localStorage**, без `sanitize()` и
без исправлений на месте. Проверяются ID материалов, типы и размеры списков,
счётчики 0…1 000 000 000, `correct <= answered`, реальные календарные даты,
активность 0…10 000 за день, диапазоны due/interval/ease/rep, объекты настроек и
профиля, язык, уровень и длина имени. Отсутствующие поля допускаются согласно
SQL-значениям по умолчанию. Дубликаты отмечаются предупреждением.
Для лимита снимка 2 MiB используется консервативная верхняя оценка размера:
крупный JSON требует отдельной проверки размера серверного jsonb и может
получить блокировку даже при фактическом размере ниже лимита.

**Обнаружено исходное расхождение:**

- замороженный SQL-манифест и сообщённый пользователем реальный облачный снимок:
  `static-ce7dd1b7fad07d9d` (revision 0);
- текущие статические файлы по `current_manifest()`:
  `static-afaa62b7426e09a7`;
- ID/количества слов, уроков, книг, видео и тем совпадают; расходится версия,
  которая учитывает содержимое файлов.

Поэтому для указанного реального облачного снимка предпросмотр вернёт
`CONTENT_VERSION_UNVERIFIED_OR_MISMATCH`, `compatible: false`, даже если структура
локального JSON корректна. Материалы и миграции в рамках задачи не исправлялись.
Нужно отдельно выяснить и согласовать различие контента. Версия локального
каталога закреплена в app.js и проверяется тестом по фактическому хешу файлов.

Это предварительная клиентская проверка, а не гарантия успешного RPC. Снимок
`sl_get_progress()` не раскрывает все строки, сессии и историю импортов:
нулевые показатели и revision 0 сами по себе не доказывают `empty_only`-допуск.
Сервер проверяет допуск, конкурентную revision, ограничения и дедупликацию.

`sl_import_progress()` принимает локальную форму списков, reviews, activity и
счётчиков; отдельного преобразования учебных полей не требуется. Однако:

- Имя применяется только к пустому облачному имени, язык/уровень — при пустом
  учебном аккаунте. Аватар, скорость, timezone и прочие поля остаются только
  внутри архивного снимка, если передать их; импорт не переносит фото в Storage.
- `independent` **складывает** XP, answered, correct и дневную активность.
  Это не выбор максимума и не универсальная дедупликация.
- Изученные слова, завершённые уроки и книги объединяются. Существующие облачные
  намерения для избранного и видео сохраняются; облачное расписание повторений
  имеет приоритет. Точный результат нельзя вывести из одних видимых списков.
- `archive_only` тоже записывает данные в облако и увеличивает revision.
  Это не предпросмотр; в этой задаче его не вызывали.

## Безопасный порядок будущего переноса

1. Оставить текущий существующий аккаунт; проверить его владельца и точный UUID
   источника. Проверить аккаунтный локальный ключ. Если прогресс есть только
   у гостя или в старой копии, отдельно подтвердить владельца и согласие на
   использование именно этого источника.
2. До любых записей сохранить неизменяемую копию выбранного исходного JSON
   отдельно от рабочего состояния. Не удалять существующие копии и хранилища.
   Проверить дату, состав и принадлежность копии.
3. Разобраться с несовпадением content_version. Повторить предпросмотр и устранить
   ошибки формата без изменения оригинала. Отдельно решить судьбу фото и
   неподдерживаемых полей. Сохранить согласованный снимок, который будет импортирован.
4. Перед согласованным импортом остановить обучение на устройствах, заново
   получить облачный снимок и проверить активный аккаунт, показатели и revision.
   До разрешения всех конфликтов не подключать отправку учебных событий.
5. Предпочесть `empty_only`, если сервер допускает перенос в пустой учебный
   аккаунт. Существующий Auth-аккаунт не обязательно имеет учебный прогресс.
   При отказе из-за непустого аккаунта остановиться и повторить сравнение;
   не переключаться на `independent` автоматически.
6. Для непустого аккаунта отдельно согласовать действие: архивирование
   `archive_only` либо `independent` только при явном подтверждении независимости
   счётчиков и отсутствии пересечения. При неясном пересечении оставить данные
   отдельно до разработки согласованного разрешения конфликтов.
7. Для будущего явно разрешённого запроса зафиксировать стабильные importId и
   sourceId UUID, точный снимок, mode и expectedRevision. При сетевой неопределённости
   не генерировать новые ID. При `40001` перечитать облако и пересмотреть решение;
   не повторять автоматически с новой revision. При разрешении архива использовать
   его исходные importId, sourceId и точный снимок.
8. После успешного переноса перечитать облако и сравнить ожидаемые результаты.
   До отдельной реализации синхронизации локальное обучение продолжает сохраняться
   локально; этот этап не включает облачные записи. Оригиналы и резервные копии
   оставить для проверки и восстановления.

аккаунтного ключа по умолчанию, отдельный гостевой просмотр, повреждённый JSON,

проверен чтением миграций, без обращения к реальному Supabase.
