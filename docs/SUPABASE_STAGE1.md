## Почему семь таблиц вместо одиннадцати

1. `sl_accounts`: профиль + настройки + общие счётчики + ревизия и флаг удаления.
2. `sl_words`: знания, избранное и SRS в одной строке слова.
3. `sl_sessions`: попытки тренировок, квизов и уроков.
4. `sl_lessons`: результаты прохождения уроков.
5. `sl_content`: прочитанные книги и отметки видео.
6. `sl_events`: неизменяемый журнал действий и ключи идемпотентности.
7. `sl_imports`: исходные снимки и принятые исторические остатки.

Отдельные `profiles`, `user_settings`, `word_favorites`, `user_sync` не нужны.
Дневная активность вычисляется из `sl_events.activity_delta` и
`sl_accounts.legacy_activity`: отдельного источника правды `activity_daily` нет.
При будущих объёмах можно добавить проверяемую проекцию, не меняя правила учёта.

Точные поля, типы, CHECK и FK описаны в `202610170001_core.sql`.

| Таблица | Ключ и основные данные |
|---|---|
| `sl_accounts` | PK/FK `user_id → auth.users`; имя, путь аватара, язык, уровень SFI, скорость речи, timezone, XP, answered/correct, legacy_activity, revision, deletion_requested_at, created_at/updated_at |
| `sl_words` | PK `(user_id, word_id)`; is_known/is_favorite, learned_at, due_at, interval_days, ease, repetitions, last_reviewed_at, scheduler_version, updated_at |
| `sl_sessions` | PK `(user_id, id)`; mode/context_id/content_version, questions (только привязки к ID), answered/correct, status, started_at/finished_at |
| `sl_lessons` | PK `(user_id, lesson_id)`; completed/completed_at, best_percent, last_session_id, updated_at |
| `sl_content` | PK `(user_id, content_type, content_id)`; book/video, is_completed/completed_at, updated_at |
| `sl_events` | PK `(user_id, event_id)`; исходный request, тип, session_id/question_index, occurred_at/received_at, activity_date/timezone, серверные deltas, revision/rules_version |
| `sl_imports` | PK `(user_id, import_id)`; уникальные source_id и snapshot_hash в пределах владельца; полный snapshot, mode, applied_revision, created_at |

Все пользовательские записи каскадно удаляются через `sl_accounts`, которая ссылается
на `auth.users`. Ссылки на попытки составные: `(user_id, session_id)` и
`(user_id, last_session_id)` не могут ссылаться на чужую попытку.
Индексы: срок повторения, недавние тренировки, день активности, ревизия событий;
уникальный индекс запрещает второй ответ на один вопрос одной попытки, даже с новым UUID.

1006 слов, 50 уроков (A:12/B:14/C:12/D:12), 12 книг, переводы и фотографии остаются
статическими. В приватной SQL-функции `sl_private.manifest()` заморожены только
допустимые ID, количества вопросов и версия контента. Это не таблица учебных материалов.
Включены ID старых и текущих видео, чтобы старый прогресс не потерял отметки.
`scripts/check_supabase_manifest.py` проверяет соответствие текущим файлам без записи.
При изменении контента создаётся НОВАЯ миграция manifest; уже применённую не редактировать.
Старые вопросы/версии при будущих релизах потребуется поддержать до опустошения
старых очередей. На этапе 1 поддержана одна текущая версия; ошибка версии сохраняет
исходное действие в очереди для последующего разрешения.

## Контракт RPC

### `sl_get_progress()`

Инициализирует строку аккаунта по `auth.uid()`, берёт ту же блокировку, что писатели,
и возвращает согласованный JSON `{revision, content_version, state}`. `state`
содержит знакомые `known`, `favorites`, `reviews`, `completed`, `videos`, `booksRead`,
`activity`, `answered`, `correct`, `xp`, `settings`, `profile`.

`profile.avatarPath` — путь в закрытом Storage, а не base64 и не постоянный URL.
Frontend следующего этапа должен получать signed URL и отображать тот же аватар.
Ранг остаётся `floor(xp/500)+1`, прогресс ранга — `xp % 500`; streak рассчитывается
по положительным дням активности существующим способом. Эти производные не хранятся
независимыми счётчиками.

### `sl_apply_event(p_event_id uuid, p_expected_revision bigint, p_event jsonb)`

Пример тела (параметры RPC передаются отдельно):

```json
{
  "type": "flash_grade",
  "occurred_at": "2026-10-17T10:00:00Z",
  "timezone": "Europe/Stockholm",
  "data": {"word_id": "v-arbeta", "correct": true}
}
```

Один UUID генерируется ДО локального сохранения действия и навсегда сохраняется
в очереди вместе с исходным телом. Ретраи используют те же UUID/тело, включая время.
`p_expected_revision` можно обновить только после корректного разрешения конфликта.

| type | data |
|---|---|
| `session_start` | `session_id`, `mode`, необязательный `context_id`, `content_version`, `questions: [{"word_id":"..."}, {}]` |
| `answer` | `session_id`, `question_index` (с нуля), `correct` boolean |
| `session_finish` / `session_abandon` | `session_id` |
| `mark_known` / `mark_review` | `word_id` |
| `flash_grade` | `word_id`, `correct` boolean |
| `favorite_set` | `word_id`, `value` boolean |
| `book_read` | `content_id` |
| `video_set` | `content_id`, `value` boolean |
| `profile_update` | непустой patch: `name` и/или `avatar_path` (null снимает аватар) |
| `settings_update` | непустой patch: `language`, `level`, `speech_speed`, `timezone` |

mode включает текущие 14 режимов, а также lesson/book/topic/review/video.
У lesson/book/topic/video context_id обязателен. Для остальных он отсутствует.
Для урока/книги количество вопросов проверяется по manifest. Все текущие уроки
имеют не более 14 вопросов, поэтому это соответствует действующему набору урока.
Вопросы не содержат тексты или ответы: только позиции и необязательный word_id.
Ответ связывается с сохранённым вопросом; передать чужой word_id отдельно нельзя.

Алгоритм транзакции:

1. Получить владельца из JWT (`auth.uid()`), создать/заблокировать его аккаунт.
2. Проверить event_id: идентичный запрос вернуть как duplicate без изменения данных,
   даже если переданная ревизия уже устарела. Другое тело с тем же ID — ошибка.
3. Проверить ожидаемую ревизию, допустимые ключи, типы, ID, время и часовой пояс.
4. Обновить попытку/SRS/отметки; вычислить XP и activity на сервере.
5. Увеличить ревизию и записать неизменяемое событие; вернуть новый снимок.

Все шаги атомарны. Исключение откатывает всю транзакцию, включая созданные строки.
Время должно иметь Z/явное смещение, быть конечным, не раньше 2000 года и не более
чем на 5 минут в будущем. Старые офлайн-события принимаются; время пользователя
не является доказательством реального времени занятия.

### Сохранённые учебные правила

| Действие | XP и активность |
|---|---|
| Ответ квиза | верно +12, неверно +3; answered +1, correct при успехе; touch +1 |
| «Знаю» | +8 и touch только при первом is_known; SRS success при каждом отдельном действии |
| Оценка карточки | верно +8, неверно +2; touch; успех отмечает is_known |
| «Повторить» | без XP; touch; SRS failure; is_known не снимается |
| Прочитана книга | первый раз +20 и touch |
| Видео отмечено просмотренным | переход false→true: +5 и touch; снятие отметки без XP/touch |
| Завершён урок | >=60%: отметка; +35 и touch только за первое прохождение |
| Имя/аватар | touch +1, как текущий profile edit |
| Настройки/избранное/начало попытки | без XP/touch |

Существующая логика намеренного снятия и повторной установки отметки видео снова
начисляет +5. Она сохранена. Повтор сетевого запроса, одинаковый event_id или повтор
`video_set=true` без снятия отметки награду не повторяет. Устранение самой возможности
получать XP за намеренный rewatch потребовало бы отдельного изменения учебных правил.

SRS: старт ease=2.5; успех: rep+1, интервалы 1, 3, затем round(old_interval*old_ease),
ease=min(3,ease+.08). Ошибка: rep=0, interval=0, ease=max(1.3,ease-.18), due через
600 секунд. Успешный интервал считается в 86400-секундных днях, включая смену DST.
Расчёт использует numeric и положительное round, соответствующее Math.round.
При двух устройствах применяется порядок принятия сервером, а точка времени для
SRS — max(occurred_at,last_reviewed_at), чтобы позднее событие не откатило часы назад.
Пределы хранения: interval <=365000 дней, rep <=100000. Значения за пределами вызывают
ошибку, а не скрытое обрезание; исходный импорт можно сохранить в archive_only.

### Конфликты двух устройств

Единая блокировка `FOR UPDATE` строки аккаунта сериализует записи только одного
пользователя. Все изменения, включая настройки и импорты, увеличивают revision.
Два разных события с одной ожидаемой ревизией: одно принимается, другое получает
SQLSTATE `40001` (`revision_conflict`) без побочных эффектов.

Следующий frontend должен после конфликта получить свежий snapshot. Добавочное
учебное событие можно повторно применить с его прежним UUID/телом и новой ревизией,
сохраняя порядок очереди. Старое намерение изменить избранное/профиль/настройки нельзя
автоматически повторять поверх новых значений другого устройства: нужен выбор
пользователя или подтверждённое новое намерение. Бесконечный retry недопустим.

Глобальная ревизия даёт несколько лишних конфликтов на разных словах, но исключает
потерю данных и существенно проще нескольких конфликтующих часов/CRDT. Для масштаба
Svenska Lätt это обоснованный компромисс.

## Перенос старого прогресса

`sl_import_progress(p_import_id, p_expected_revision, p_source_id, p_state, p_mode)`.

- `empty_only` (по умолчанию): аккаунт без учебных данных; переносит исторические
  счётчики ровно как остаток, без начисления наград за импортированные отметки.
- `archive_only`: хранит полный снимок, не меняет прогресс/XP. Подходит для неизвестных
  ID, спорной истории и аватара. Архивирование увеличивает ревизию.
- `independent`: пользователь ЯВНО подтвердил, что история не пересекается с имеющейся.
  Складывает счётчики и активность; объединяет known/completed/books. Облачные
  избранное, отметки видео, существующие SRS-расписания и настройки имеют приоритет.
  Имя заполняется, если пустое. Этот режим нельзя выбирать автоматически.

Неизменяемый снимок хранится целиком, включая base64 аватара, неизвестные поля и
исторические значения. MD5 канонического jsonb используется только для поиска
одинаковых снимков; при совпадении дополнительно сравнивается весь JSON. Это не
механизм проверки подлинности. Дедупликация действует по владельцу + import_id,
source_id и snapshot_hash. Одинаковые исходные данные нельзя повторно прибавить
путём смены UUID. Один source_id — один исходный снимок/граница переноса.

Архивированный снимок можно явно применить позднее с теми же import_id/source_id,
тем же JSON, новой ревизией и подходящим режимом. Повторное применение уже принятого
снимка не увеличивает XP. Другой снимок с прежней идентичностью отклоняется.

Перед frontend-интеграцией необходим UI предварительного результата. Порядок:

1. Скопировать `sv-guest-v2` в неизменяемый локальный backup и дать скачать JSON.
2. Зафиксировать source_id/import_id и границу перехода; после снимка все новые
   действия получают event_id и НЕ включаются повторно в тот же baseline.
3. Проверить снимок; неизвестные ID/невалидные значения не удалять. При споре сначала
   archive_only и отчёт. Автоприменение неизвестных ID запрещено.
4. Для пустого аккаунта — empty_only. Для доказанно независимой истории — independent
   после явного подтверждения. Для пересекающихся копий не использовать сумму/максимум
   молча: оставить архив, показать различия и подготовить отдельное решение с пользователем.
5. Проверить серверный результат, затем отправить только события после границы.
6. Сохранить исходный localStorage/backup. Ни одна SQL-функция не может удалить его.

Исторические даты learned_at/completed_at и результаты отдельных старых квизов
не изобретаются. Интервал/rep/ease и due переносятся точно, due из миллисекунд в UTC.
Даты `activity` не меняются: исходный timezone не сохранён. Несовместимые счётчики
(например correct>answered) отклоняются, исходный снимок доступен для archive_only.
При independent спорные SRS и профиль доступны в исходном snapshot для явного выбора.
Пересекающиеся разные старые снимки нельзя безошибочно дедуплицировать по действиям:
в них этих ID нет. Это ограничение данных, а не обещанная автоматическая миграция.

Аватар из snapshot позднее загружается отдельной операцией в Storage, затем
profile_update задаёт путь; старый base64 остаётся в исходной копии.
Выбранный системный голос и cookie choice остаются на устройстве. Язык гостя
доступен без Auth. Скорость озвучивания можно передать settings_update без XP.

SQLite: экспортировать state каждого пользователя после резервного копирования БД;
подтвердить принадлежность email и связать с новым Auth UUID. PBKDF2-хеши паролей,
локальные числовые ID и svsession не импортировать. Использовать новый пароль/сброс
через Auth; проверить отдельно, что Python clean_state не сохранил профиль.

## RLS, EXECUTE и доверие

- Семь таблиц: RLS включён, `authenticated` имеет только SELECT собственных строк
  по `(select auth.uid())=user_id`. У `anon`/PUBLIC нет доступа к данным.
- Прямые INSERT/UPDATE/DELETE отозваны. Все пользовательские записи идут через RPC.
- Публичные RPC имеют `SECURITY DEFINER SET search_path=''`, полные имена объектов,
  не принимают владельца от клиента и проверяют `auth.uid()` до чтения данных.
- Приватные функции — SECURITY INVOKER в схеме без USAGE/EXECUTE для клиентов.
- EXECUTE PUBLIC/anon/authenticated отозван явно; authenticated возвращён EXECUTE
  только на четыре RPC и read-only policy helper `sl_avatar_access(text)`.
- Нет динамического SQL из пользовательского ввода. Динамический DDL в первой
  миграции использует закрытый список имён и `%I`; в runtime RPC его нет.
- Клиент не задаёт xp_delta, score, interval, ease, user_id. Правила серверные.
- Корректность ответа заявляет клиент, как и в текущем приложении со статическими
  ответами. Это персональный учебный трекер, не доверенный экзамен/рейтинг.
- Вызовы слежения за аккаунтами/триггеры Auth не нужны: аккаунт создаётся лениво
  при первом RPC. При регистрации frontend должен сохранить введённое имя отдельным
  действием или использовать существующий Auth metadata до редактирования профиля.
- Запускать миграции ролью `postgres` (Dashboard SQL Editor/официальный migration
  workflow), не менять владельца функций на клиентские роли.

Обоснования: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security),
[безопасность функций](https://supabase.com/docs/guides/database/functions),
[Storage](https://supabase.com/docs/guides/storage/security/access-control),
[управление пользователями](https://supabase.com/docs/guides/auth/managing-user-data).

## Storage и удаление аккаунта

Миграция создаёт закрытый bucket `avatars`: <=1 MiB, JPEG/PNG/WebP. Это ограничение
уже обработанного файла 240×240, а не исходного фото до 6 MiB в текущем интерфейсе.
Путь: `<auth.uid()>/<unique-file-id>.jpg|jpeg|png|webp`, без подпапок и `..`.
Все четыре Storage-политики ограничены bucket, владельцем пути и активным аккаунтом.
UPDATE проверяет и старую, и новую строку. Политики других bucket не изменяются.
Для отображения нужны короткоживущие signed URL. При замене лучше загрузить новый
уникальный путь, подтвердить profile_update, затем удалить старый файл через API.

Удаление не ограничивается SQL CASCADE: Auth не следует удалять до очистки файлов.

1. После подтверждения пользователя вызвать `sl_request_account_deletion(revision)`:
   замораживает учебные записи и доступ/загрузки аватаров, повтор вызова безопасен.
2. Доверенный сервер проверяет JWT, получает UID из него, отзывает/закрывает сессии,
   через Storage API перечисляет и удаляет все аватары UID, включая неиспользуемые.
3. Учитывает уже начатые до заморозки загрузки: дожидается завершения/таймаутов,
   повторно перечисляет файлы и повторяет cleanup при сбое. Затем вызывает Auth Admin
   delete; отказ из-за оставшихся объектов требует повторного cleanup, а не обхода
   проверки. Действующие signed URL могут работать до истечения их срока.
4. SQL CASCADE удаляет все семь пользовательских наборов, включая снимки с base64.

Нельзя удалять production storage.objects напрямую: останутся реальные файлы.
Реализация доверенного серверного обработчика/Auth Admin API — следующий этап;
SQL этого этапа готовит заморозку и связи, но сам HTTP cleanup не выполняет.
При отмене/сбое удаления аккаунт остаётся pending; разблокировка требует проверенной
серверной операции, а не произвольного frontend UPDATE.

## Применение к НОВОМУ проекту — только вручную после одобрения

На текущем этапе ничего из этого не выполнялось.

1. Создать Supabase-проект вручную; выбрать подходящий регион и сохранить серверные
   секреты вне репозитория. Подготовить постоянную резервную копию исходных файлов.
2. Убедиться, что нет `learning_progress`, bucket `avatars` и других `sl_*` объектов.
   Если есть — остановиться, сначала проанализировать существующие данные/политики.
3. В Dashboard → SQL Editor под `postgres` выполнить целиком, строго по порядку:
   - `supabase/migrations/202610170001_core.sql`
   - `supabase/migrations/202610170002_manifest.sql`
   - `supabase/migrations/202610170003_progress_rpc.sql`
   - `supabase/migrations/202610170004_import.sql`
   - `supabase/migrations/202610170005_avatars.sql`
4. Каждый файл — отдельная транзакция. При ошибке остановиться и исправить причину,
   не пропуская строки и не выполняя старый SUPABASE_SETUP.sql. Уже успешные файлы
   не запускать повторно; они намеренно не скрывают конфликты через IF NOT EXISTS.
   Для истории Dashboard-применения записать имена/даты; при будущем переходе на CLI
   согласовать migration history до использования db push.
5. Проверить семь таблиц, RLS, SELECT-политики, отсутствие клиентского DML/доступа anon,
   закрытый bucket, лимиты/MIME и четыре политики Storage. Security Advisor без
   критических замечаний; не выдавать PUBLIC EXECUTE «для исправления ошибок».
6. В Auth настроить подтверждение email, минимальную длину пароля не ниже текущих
   8 символов, доставку писем/SMTP и точные URL возврата/восстановления с учётом
   реального подкаталога GitHub Pages. Это настройки проекта, не SQL-миграции.
7. Проверить отдельно на локальном Supabase/тестовом проекте HTTP Auth, refresh/logout,
   двух реальных пользователей, signed URL, ограничения загрузок и полный cleanup.
   `bootstrap_local.sql` туда НЕ загружать. `001_contract.sql` — только одноразовая
   локальная/тестовая БД; он создаёт фиктивных Auth-пользователей и откатывается.
8. Не заполнять supabase-config.js и не менять app.js до утверждения следующего этапа.
   Текущий frontend несовместим с новым RPC-контрактом и не начнёт использовать его
   автоматически. Не открывать старые прямые права ради совместимости.

## Тесты и границы проверки

Команды из корня проекта:

```sh
python3 scripts/check_supabase_manifest.py
python3 scripts/test_supabase_local.py
```

Тестовый runner не принимает адрес БД, удаляет PG* из окружения и создаёт новый
кластер в /private/tmp. TCP отключён, Unix socket доступен только владельцу.
После проверок сервер останавливается; каталог с журналами остаётся.
При sandbox-ошибке shared memory нужен разрешённый запуск этих локальных тестов;
это не подключение к Supabase и не выполнение миграций на удалённом сервере.

SQL-тесты проверяют реальные Postgres grants/RLS/FK/транзакции, используя минимальные
заглушки auth.uid()/auth.users/storage.*. Проверки с параллельными psql-соединениями
покрывают одинаковый UUID, разные изменения профиля и повторное применение учебного
события после конфликта. Защита старой learning_progress проверяется в отдельной
одноразовой БД.

Это не запуск Supabase Auth/GoTrue, PostgREST или Storage HTTP backend. Доставка email,
реальные JWT, MIME/размер на Storage API, signed URLs, Admin API удаления и frontend
на телефоне остаются обязательной проверкой следующего этапа. Никаких внешних
подключений или тестов на реальных пользовательских данных не было.
